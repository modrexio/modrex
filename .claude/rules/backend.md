### Rust backend modules (`src-tauri/src/commands/`)

Paths in this rule are relative to `apps/desktop` unless they already start with
`apps/desktop`.

**App startup sequence** (`src-tauri/src/lib.rs` setup hook, fires before the window shows): `migrate_from_electron` runs synchronously first, then fire-and-forget: `cleanup_thumbnail_cache` and the `mod_index` snapshot refresh (`ensure_index`).

**Logging**: `tauri_plugin_log` writes to `Modrex.log` in the app's log dir (`%LOCALAPPDATA%\Modrex\logs\` on Windows — note this differs from `app_data_dir()`'s `%APPDATA%\Modrex\` used for `settings.json`/`mod-index.db`), level `Warn` globally and `Info` for the `modrex_lib` crate, 5 MB with one rotated backup kept. Reachable in-app via Settings > Logs ("Open log file", which copies it to `%TEMP%\modrex_log.txt` first). `install_mod`/`install_file` log every error path via `log::warn!` (not just the final install/state-write phase) so a failed install/update is always diagnosable from the log — when adding a new `?`-early-return inside either function, route it through the same log-then-return pattern rather than a bare `?`.

- **`settings.rs`** — reads/writes `settings.json` in Tauri's `app_data_dir()` (`%APPDATA%\Modrex\` on Windows, `~/.config/modrex/` on Linux). Top-level fields: `skipFileOpenLogWarning`/`dismissedDepsWarnings` (global flag + list, PD3-only warning — see TopBar), `games: Option<HashMap<String, GameSettings>>`. `GameSettings` holds `game_path?`/`launcher?` (genuinely optional — not-yet-detected) plus `install_pinned` (see the launcher section: the two path fields name one store's copy together, and there is deliberately **no command that writes `launcher` on its own** — the removed `set_launcher` was exactly that, and it let Modrex mod one copy while launching another) plus `launch_options`/`suppress_crash_reporter`/`crimeboss_install_mode` per game. The latter three, and every `Settings` field with a well-defined default (`skip_file_open_log_warning`, `dismissed_deps_warnings`, `analytics_consent_asked`, `analytics_enabled`, `discord_rich_presence_enabled`, `successful_installs`, `first_install_at`, `support_prompt_shown`), are plain non-`Option` types with `#[serde(default[ = "fn"])]` rather than `Option<T>` — `null` never appears in settings.json for a field that only ever means "use the default"; `Option` is reserved for fields with a real third state (not-yet-detected paths/launcher, `analytics_id`, `nexus_oauth`, or the legacy flat fields below). Both `GameSettings` and `Settings` have hand-written `impl Default` (not derived) because two fields default to a non-zero value (`discord_rich_presence_enabled: true`, `crimeboss_install_mode: "auto"`) that `#[derive(Default)]` wouldn't produce. Legacy flat fields (`game_path`, `launcher`, `launch_options`) carry `#[serde(skip_serializing, default)]` so old settings files still deserialize but writes always use the new `games` map. `migrate_settings(s: Settings) -> Settings` promotes legacy flat fields to `games["pd3"]` on first read — called inside `read_settings`. `game_settings<'a>(s, game_id) -> Option<&'a GameSettings>` is the canonical helper for reading per-game config; always use it instead of touching legacy fields directly. Commands: `get_game_settings(game_id: String) -> GameSettings` (new); `set_launch_options`, `configure_game_path`, `detected_installs`, `set_suppress_crash_reporter` all accept `Option<String> game_id` defaulting to `"pd3"` for backwards compatibility. On first launch after the Electron-to-Tauri migration, `migrate_from_electron` copies `settings.json` and `mod-index.db` from the old Electron path (`%APPDATA%\PD3 Mod Manager\` on Windows, `~/.config/pd3-mod-manager/` on Linux). Called from `lib.rs` setup hook before the window shows. `reset_app_settings` factory-resets settings.json to `Settings::default()` through `update_settings` (clearing every game path, launcher choice, analytics consent + id, and preference); it never touches installed mods, game files, or the on-disk caches. The renderer pairs it with wiping all `modrex:` localStorage keys and reloading, for a genuine first-run reset.

- **`api.rs`** — modworkshop REST API via `reqwest` (Cargo features `gzip`+`brotli` negotiate response compression — ~5x smaller payloads, e.g. a 24-mod listing page is 115 KB raw vs 21 KB brotli, verified live; no code involved beyond the `Cargo.toml` feature flags). Params sent as query string (GET requests). `get_mod` returns extra fields (`images`, `banner`, `dependencies`, `instructs_template`, `tags`) absent from `list_mods` results; `list_mods` also accepts a repeated `ids[]` param (`ListModsParams.ids: Option<Vec<u32>>`) — an undocumented modworkshop feature, verified live (`/games/{id}/mods?ids[]=A&ids[]=B` returns exactly those mods, list-item shape) — that turns a bulk metadata refresh into one request per ~50 ids instead of one `get_mod` per id; see `fetchInstalledModsMeta` in `modCache.ts`. `list_mods` also takes `tags`/`block_tags` (`Option<Vec<u32>>`, sent as repeated `tags[]`/`block_tags[]`) for the Browse tag filter: `tags[]` matches mods carrying **any** of the ids, `block_tags[]` matches mods carrying **none** — both membership filters (OR within each list, not all-of), capped at 10 each server-side. `list_tags(game_id)` fetches the game's mod-tag catalog from `/games/{id}/tags?type=mod&global=1`; use `global=1`, not `global=true` — modworkshop's Laravel `boolean` rule 422s on the string `true` — and `global` folds in site-wide tags on top of the game's own while the server drops any the game hides. Its default page size is 50 (the API's max `limit`). modworkshop enforces **90 req/min per IP, shared across every endpoint** (read from the `x-ratelimit-limit`/`x-ratelimit-remaining` response headers — not documented anywhere by modworkshop, and there's currently no API-key tier to request a higher one). Three-layer request control: (1) `RATE_LIMITER` token bucket (burst 4, 1.3 req/s sustained ≈ 78/min — deliberately under the real 90/min, not over it: an earlier burst-8/4-per-sec version was 2.7x over and self-inflicted 429s); (2) `RATE_REMAINING`, an `AtomicI64` updated from `x-ratelimit-remaining` on every response (success or 429) — when it reads ≤ 5, `api_get` adds a flat 3 s pause before the next send, so the client backs off proactively instead of only reacting after a 429 already happened; (3) `API_SEMAPHORE` caps concurrent in-flight requests at 3. On 429 the semaphore permit is released and the request is retried up to 3 times with exponential backoff (1 s / 2 s / 4 s jitter) or the `Retry-After` header value. Shared `HTTP_CLIENT` static (connection pooling via `pool_max_idle_per_host(4)`). **HTTP_CLIENT invariant**: every outgoing HTTP request anywhere in the Rust backend must go through `http_client()` from `api.rs` — never call `reqwest::Client::new()` directly. Creating a new client bypasses connection pooling and drops the `User-Agent` header that modworkshop requires. Both `http_client()` and `user_agent(app)` are `pub(crate)` — import them via `use crate::commands::api::{http_client, user_agent}` when making HTTP requests from outside `api.rs`.

- **`domain.rs`** — the neutral mod shapes every source translates into, plus the ModWorkshop and Nexus translations. **Two structs per shape, and the split is load-bearing**: the private `Wire*` types carry a container-level `serde(default)` and are what the API actually sends; the public types (`ModSummary`, `ModDetail`, `ModFile`, `ModLink`, `ModPage`, `FilePage`, `LinkPage`) have **required** fields and are what crosses IPC. Two reasons for that shape. (1) These used to cross as untyped JSON that TypeScript only claimed to know, so a missing field rendered as a blank label; deserializing into a struct without defaults turns the same response into a hard error that empties the whole browse page. (2) specta derives optionality from the serde attributes, so one struct carrying both derives plus `serde(default)` exports EVERY field as optional in TypeScript, which is weaker than the hand-written types it replaced. **`null_default` on every non-Option wire field is not decoration**: `serde(default)` fires for an ABSENT field only, and ModWorkshop sends explicit nulls (a mod with no category sends `"category_id": null`), which produced a live `invalid type: null, expected i64` that failed entire listings. Public entry points are `parse_mod_page`, `parse_file_page`, `parse_link_page`, `parse_mod_detail`, `parse_nexus_page`. `ModDetail` reuses `WireModSummary` through `serde(flatten)`; a test asserts both halves land from one payload, because if flatten ever stops merging, the summary half silently comes back as defaults. `ModDependency.target` is a `ModSummary`, not a detail — ModWorkshop returns the listing shape there, the deps tab only reads summary fields off it, and typing it as a detail would make the type recursive for nothing. The **Nexus mapping is lossy on purpose** and documented at the function: endorsements stand in for likes, `pictureUrl` rides the thumbnail field as an absolute URL (which `useThumbnail` passes through untouched), and **version is deliberately empty** because the GraphQL search selection carries none — an empty version is what suppresses false update prompts in `useModData`, so filling it with a placeholder would make every Nexus mod nag forever.

- **`sources.rs`** — the mod-source registry: which sources exist, which games each serves, and the id each knows a game by (`SourceSpec { id, games: &[SourceGame { game_id, native_id }] }`). `native_id` is a string because the two kinds are not alike: ModWorkshop uses a numeric game id, Nexus a domain slug. `nexus_domain` and `game_id_for_domain` derive from it rather than restating the mapping. `list_sources` hands it to the renderer (`src/renderer/src/sources.ts`), which is how the Browse source switcher knows a game has more than one source; `GAME_SPECS` no longer carries `nexusDomain`. `pnpm check-sources` diffs the ModWorkshop half against `GAME_SPECS.workshopId`, which the renderer still uses directly; Nexus is deliberately NOT checked there because the renderer reads it from this registry at runtime, so there is no second list to drift. `source_native_local_id(source_id, remote_id) -> i64` is what `InstalledMod.id` is derived from once a mod is identified, for every source including ModWorkshop — an FNV-1a hash of `"{source}:{remote_id}"`, forced negative (`((hash >> 1) as i64).max(1)` negated). No source is privileged with a raw real id: the earlier scheme (ModWorkshop's real positive id, everything else `-remote_id`) let two different non-ModWorkshop sources collide on the same numeric id, and separately made ModWorkshop an implicit default source in code that had to special-case it. `id` is opaque and never sign-meaningful for any source now; the real id always lives in `InstalledMod.remote_id: Option<String>` — see the `InstalledMod.id` fact in the root `CLAUDE.md`.

- **`download.rs`** — streams file to `temp_dir()/modrex-{uuid}.{ext}`, emitting `download:progress` Tauri events with `{ downloaded, total }`. `total` is `0` when the server omits `content-length` — callers must handle the indeterminate case.

- **`mods/`** — the most complex module, split into focused subfiles. `mod.rs` holds all `#[tauri::command]` functions and re-exports; the logic lives in:
    - **`StateLocks` (in `mod.rs`)** — per-game async locks serializing every read-modify-write of a game's `.modrex.json`. `save_state` is atomic per _write_, but two interleaved commands (an `nxm://` install landing mid focus-refresh, say) can each read the same state and the second write silently drops the first's changes. Every mutating command takes the guard via `lock_game_state(&app, game_id).await` before its read-modify-write span. Keyed per game so different games stay parallel. **Never hold a guard across a network download** — acquire it around the disk-write + state span only, or a slow download blocks every other operation on that game.
    - `engine.rs` — `ModEngineConfig` parameterizes all engine behavior per game. Fields: `game_id`, `index_game_name` (matches `games.name` in `index.db` — "PAYDAY 3", "PAYDAY 2", "PAYDAY: The Heist", "Crime Boss: Rockay City", "RAID: World War II"), `state_filename`, `targets: &'static [ScanTarget]`. `ScanTarget` holds `tag: &'static str`, `unit: ModUnit`, `mods_subpath`, `disabled_subpath`, `backup_subpath`. `ModUnit` enum: `File { extension, disabled_suffix, priority_prefix }` for UE pak games (PD3 and Crime Boss, both UE 4.27 — same `.pak`/`~mods` convention); `Directory { entry_markers, scan_markers, index_gated_markers, excluded_names, priority_prefix }` for Diesel/BLT games (PD2, PDTH) and the `ue4ss_mods` target on PD3/Crime Boss. **`entry_markers` vs `scan_markers`**: `entry_markers` drives archive classification during install (`classify_archive_dirs`, `is_unplaceable_pack`); `scan_markers` drives ambient disk scanning (`scan_active`, `scan_disabled` in `paths.rs`) — they are intentionally separate. PDTH mods has `entry_markers: &["mod.txt", "base.lua"]` (so DAHM sub-mod ZIPs install correctly) but `scan_markers: &["mod.txt"]` (so DAHM's ~40 bundled framework modules, which have `base.lua` but no `mod.txt`, are not auto-discovered as untracked mods) — `base.lua` instead sits in `index_gated_markers`, so those folders are _discovered_ but only tracked if their SHA256 matches the mod index. `excluded_names: &'static [&'static str]` is a third, name-based filter for when index-gating can't apply (a bundled folder's content is never hashed into the index at all — see UE4SS below); `scan_active`/`scan_disabled` skip any directory whose name appears there before even checking markers. `engine_for_game(game_id)` looks the id up in `GAME_REGISTRY` (`commands/games.rs`) and returns `Result<&ModEngineConfig, String>` — an unknown id is a hard error, never a silent PD3. `game_def_for_id` in `launchers/` does the same over the same registry. Helper fns: `mods_dir`, `disabled_dir`, `backup_dir`, `state_path`. Methods: `primary()` returns `&targets[0]`; `target_for(tag: Option<&str>)` routes by tag, falling back to primary for unknown tags; `disabled_suffix()`, `is_directory_unit()`, `priority_prefix_enabled()` (mirrors `disabled_suffix()`'s match-on-`ModUnit` shape — every site that calls `apply_priority_prefix` must gate on this first, since several targets, e.g. Crime Boss's `mods` and PD2/PDTH's `mods`/`mod_overrides`, manage order via something other than a filename prefix; `reorder.rs`, `folders.rs`, and `state.rs`'s `compact_folder_priorities` all gate on it). Every Tauri command in `mod.rs` takes a required `game_id: String` and starts with `let cfg = engine_for_game(&game_id)?` (the `?` surfaces an unknown-game error), passing `cfg` to all lower-level ops. `PD2_ENGINE` has two targets: `mods` (`entry_markers/scan_markers: &["mod.txt", "main.xml"]`) and `mod_overrides` (`entry_markers/scan_markers: &[]` — any directory). `PDTH_ENGINE` has two targets: `mods` (entry/scan markers as above) and `mod_overrides` (`entry_markers/scan_markers: &[]`). `RAID_ENGINE` has a **single blanket-accept `mods` target** (`entry_markers/scan_markers: &[]`, `excluded_names: RAID_INFRA_FOLDERS` = `base`/`downloads`/`logs`/`saves`) — **no `assets/mod_overrides` target**: RAID's current loader (RAID-SuperBLT + RAIDWW2-BeardLib) reads both BLT script mods (`supermod.xml`/`mod.xml`; no `mod.txt` in RAID's fork) and asset override packs from one `mods/<name>/` folder, since the game removed the `assets/mod_overrides` mount (it shows a "MOD OVERRIDES IS NO LONGER USED" migration dialog; BeardLib's `FindOverrides` scans each `mods/<name>/` for override subfolders instead). Markers can't be used because asset packs carry none; `excluded_names` mirrors BeardLib's own `_ignore_folders` (minus BeardLib itself, a normal installable mod), and the top-level `base` skip in `find_untracked_paks` additionally covers `mods/base/supermod.xml`. `PD3_ENGINE` has two targets: `paks` (primary, `File` unit, `.pak`/`~mods`) and `ue4ss_mods` (secondary, see UE4SS below). `CRIMEBOSS_ENGINE` has three targets, and unlike every other multi-target game its **primary** is the `Directory` one: `mods` (no markers — blanket-accept, same shape as PD2's `mod_overrides`) rooted at `CrimeBoss/Mods`, then `paks` (legacy `File` unit, `.pak`/`~mods`, same convention as PD3) rooted at `CrimeBoss/Content/Paks/~mods`, then `ue4ss_mods` (see UE4SS below). New installs always land in `mods` because `resolve_archive_download` dispatches on `cfg.primary().unit`; `paks` is reachable only via `target_for(Some("paks"))` (ambient scan/enable/disable/uninstall of pre-existing loose-triplet installs, never new installs). See the "Crime Boss" key domain fact below for why.
    - `types.rs` — `InstalledMod`, `ModFolder`, `ModsState`, `InstalledResponse`, `TopLevelItem`, `UpdateStatus`. **`UpdateStatus` (`Known`/`Unknown`/`Outdated`) replaced the old habit of encoding this in the version STRING** as `"unknown"`/`"outdated"`, which worked only because neither is a plausible ModWorkshop version and forced every reader to know both sentinels. Per-source version semantics do not fit one overloaded string either: Nexus search returns no version at all, and Steam Workshop has update timestamps rather than versions. `Outdated` specifically means a name match succeeded AFTER a SHA256 check against the index's current file already failed, so the installed bytes are known stale; `Unknown` never surfaces an update, because a mod with nothing comparable would nag forever. State files predating the field are migrated in `read_state` (NOT `reconcile_state`, which has two early returns that would bypass it) and the version is cleared, so a sentinel can never be compared as a real version. `InstalledMod.location: Option<String>` — scan target tag; `None` = primary target (backward-compatible), `Some(tag)` routes all ops to the named `ScanTarget`. Carries `#[serde(default, skip_serializing_if = "Option::is_none")]` so state files without it still deserialize.
    - `naming.rs` — `strip_priority_prefix` / `apply_priority_prefix` (filenames on disk are always `NNN_name.pak`), `pak_filename`, `hash_filename`, `make_uid`
    - `paths.rs` — `mods_base` / `disabled_base` / `get_state_path` / `active_mod_path` / `disabled_mod_path` / `find_untracked_paks`. `find_untracked_paks` iterates all `cfg.targets`; skips any target whose backup dir exists; builds a per-target known set by stripping the `"<tag>:"` prefix from keys in the caller's `known: HashSet<String>`; returns `Vec<(String, bool, Option<String>)>` — (rel*path, is_enabled, location_tag). Callers must build known keys as `format!("{}:{}", m.location.as_deref().unwrap_or(""), rel_path)`. **Host-pack paths**: `resolve_host_mod_dir` finds an installed host mod's on-disk folder by modworkshop id (from state; active → disabled → conventional name); `host_pack_dir` returns where an installed host pack lives (`<host>/<subpath>/<filename>`); `host_pack_disabled_dir` is the Modrex-managed disabled location \_outside* the host (`mods/disabled/host-<id>/<filename>`).
    - `state.rs` — `read_state`, `save_state` (atomic: writes to `{name}.tmp` then `fs::rename` over the real file — never revert to a direct `fs::write`), `get_folder_path` (recursive, builds slash-separated path from `parentId` chain), `reconcile_state` (marks missing files `missing: true`; migrates legacy `.disabled` paths; migrates `.pd3mm.json` → `.modrex.json` on first run; when backup dir exists: File-unit games read state from inside the backup because the whole folder was renamed; Directory-unit games read from the normal `state_path` because the state file stays in `mods/` and only user mod dirs were moved). `reconcile_state` also: **purges framework-only entries** — on every load, drops entries with no `file_id` and no `remote_id` (i.e. Modrex-installed or identified-by-any-source entries are always kept) that are _either_ missing all of the target's `scan_markers` files on disk (catches DAHM framework modules that were auto-discovered while the `scan_markers`/`entry_markers` split didn't exist yet) _or_ whose filename is on the target's `excluded_names` list (catches UE4SS bundled framework sub-mods collected before `excluded_names` existed — their marker file is still genuinely present, so the first check alone never catches them; Modrex-installed entries with a `file_id` are never touched); removes phantom folders (folders with no mods, no child folders, and no active directory — disabled dir is ignored so a leftover `disabled/` subdir doesn't block cleanup); calls `compact_folder_priorities` to renumber folder disk names to sequential `(1, 2, 3, ...)` within each parent scope (repairs gaps from prior bugs). **Two identity migration/repair passes**, both one-time self-healing that runs on every load until there's nothing left to fix: (1) backfills `remote_id` for a ModWorkshop entry identified before `remote_id` existed for that source — its `id` already IS the real ModWorkshop id (the only meaning `id` ever had before it became opaque for every source, see `sources.rs`'s `source_native_local_id`), so this is a plain fill-in, never a re-derivation, and it must run before `identify.rs`'s `upgrade_negative_ids` — which otherwise can't tell "genuinely never identified" apart from "identified long ago, just missing this new field," and its fuzzy SHA256/name fallback wipes the stored version and marks the mod Outdated on a name match, which must not fire as a side effect of a data migration; (2) recomputes `expected = source_native_local_id(&m.source, remote_id)` for any entry with `remote_id.is_some()` and overwrites `m.id` if it disagrees, repairing a source-native id that was ever wrongly promoted to another source's id (the root cause of a real observed bug: an exact SHA256 hit across a cross-posted file let a Nexus-tracked entry's `id` get silently reassigned to an unrelated ModWorkshop id before `upgrade_negative_ids`'s `remote_id.is_some()` guard was fixed). Both passes fold into the same single `save_state` call as everything else above.
    - `zip.rs` — multi-format archive support. `ArchiveFormat` enum (`Zip`, `SevenZip`, `TarGz`, `TarXz`, `Rar`) + `detect_archive` (magic-byte dispatch). Public API: `list_pak_entries`, `extract_entry`, `extract_dir_entry`, `extract_archive_flat`, `classify_archive_dirs`, `is_unplaceable_pack`, `resolve_archive_download`, `mark_archive_files`, `compute_sha256`. **Format dispatch**: all five formats share one enumerator — `list_entries` returns `Vec<ArchiveEntry { name, is_dir }>`, and the listing/classification operations (`list_pak_entries`, `classify_archive_dirs`) are pure functions over it; only extraction stays per-format because unrar can only extract to a directory (it can't expose a per-entry reader). `compute_sha256` streams the file in 64 KB chunks via `spawn_blocking` rather than buffering it whole. **Zip-Slip invariant**: every directory extractor (`extract_dir_*`, `extract_flat_*`) must route its destination through `safe_dest`, which rejects entries with `..`, absolute, or drive/UNC-prefix components; RAR extraction additionally validates entry names before `extract_with_base` (which writes by internal name). `resolve_archive_download` returns `ResolvedArchive` (a type alias for `Result<(PathBuf, Option<PathBuf>, Option<String>), String>`) — the third element is `location_tag` (`None` for primary, `Some(tag)` for secondary). For Directory targets it runs `classify_archive_dirs(names, cfg)`, which tags every mod dir with its destination: marker dirs (`mod.txt`/`main.xml`, at any depth via `rfind`) → their target; marker-less dirs at the **same depth** as marker dirs (or every top-level dir when the archive has no markers) → the override target; an explicit `assets/mod_overrides/<name>/` segment unwraps to the dir _inside_ it (handles packs double-wrapped in the game path). A single dir resolves directly; multiple dirs emit `ZIP_MULTI_PAK` with a single top-level `targetTag` when all entries share one target, or a parallel `entryTags` array when the archive spans targets (a mixed modpack) so the picker routes each entry independently. Two guards run before classification (PD2 only): `detect_host_pack` (see `host_mods.rs`) returns a `HOST_MOD_PACK` sentinel for content packs that install _inside another mod_, and `is_unplaceable_pack` returns `UNRECOGNIZED_ARCHIVE` for a flat folder of loose files (no marker, no nested asset structure) that can't be placed in any scan target. **UE4SS routing** (both `resolve_archive_download`'s File-unit branch and `resolve_crimeboss_archive`): when an archive has zero `.pak` entries, before erroring it first checks `has_ue4ss_loader_signature` (a top-level `UE4SS-settings.ini` — the one marker that's only ever present in the _full_ loader package, never a standalone sub-mod, since the bundled framework sub-mods ship alongside it with the exact same `Scripts/main.lua` shape a real sub-mod has) and emits an internal `UE4SS_LOADER:<zipPath>` sentinel (handled entirely in `mod.rs`, never reaches the renderer); if that's absent, `try_classify_as_directory_target` falls back to `classify_archive_dirs` against `cfg.targets` (which already includes `ue4ss_mods` for PD3/Crime Boss even though it's never primary) to catch a standalone Lua sub-mod archive. Each format has private helpers (`_zip`, `_7z`, `_tar<R>`, `_rar`). **sevenz-rust callback invariant**: the `bool` returned by the `decompress_with_extract_fn` closure controls iteration — `Ok(false)` stops, `Ok(true)` continues. Non-matching entries must drain their bytes via `std::io::sink()` before returning `Ok(true)` to stay stream-aligned in solid 7z archives. **unrar extraction pattern**: `open_for_processing()` uses a typestate loop — `archive.read_header()` moves `archive` into the returned `Header`; `header.skip()` and `header.extract_with_base(dir)` move it back. RAR extraction writes to a temp dir (the unrar API can only extract to a directory, not a single file path) then copies to `dest`; cleanup is guaranteed via an IIFE closure. `mark_archive_files` returns `(Vec<InstalledMod>, bool)` — the bool is `true` when at least one mod was newly checked (dirty flag for the caller to persist state). Skips mods where `archive_broken.is_some()` so repeated calls are O(1). `InstalledMod.archive_broken: Option<bool>`: `None` = unchecked, `Some(false)` = clean, `Some(true)` = broken; persisted in the state file so magic-byte scanning is amortized across launches.
    - `install.rs` — `install_mod_from_path`, `uninstall_mod_op`, `enable_mod_op`, `disable_mod_op`. All accept `cfg: &ModEngineConfig` and a `target: &ScanTarget` (derived via `cfg.target_for(m.location.as_deref())`). `install_mod_from_path` sets `location: None` for the primary target, `Some(target.tag)` for secondary (uses `std::ptr::eq(target, cfg.primary())`). File ops use extension rename / file copy / remove*file; Directory ops use dir move / recursive copy / remove_dir_all. Priority prefix applied only when `target.unit.priority_prefix` is true. `enable_mod_op`/`disable_mod_op` special-case `target.tag == "ue4ss_mods"`: call `ue4ss_modstxt::sync_enabled` and flip the tracked flag, then `return` *before* the file-move block runs — see UE4SS below for why moving the folder would do nothing. `launch_game` and `launch_without_mods` both call `maybe_suppress_crash_reporter` before spawning, so any future cleanup-only setting should stay launcher-gated and best-effort. `uninstall_mod_op` removes only the selected mod files and leaves now-empty app folders in state/on disk; folder removal is explicit via `delete_folder_op` or reconciliation of phantom folders whose active directory is gone. **Host packs** (`location` starting `host:` — see `host_mods.rs`) take dedicated branches in every op: `install_host_pack_op` extracts a set into the host mod's folder and records it; `uninstall_mod_op` removes from the active \_or* disabled location; `enable_mod_op`/`disable_mod_op` call `move_host_pack`, which moves the set between the host's subfolder and `mods/disabled/host-<id>/` (flipping only the `enabled` flag would leave the set loading in-game).
    - `host_mods.rs` — declarative registry of **host mods**: mods whose add-on content packs install _inside another mod's folder_ rather than at a scan-target root (the canonical case is Menu Backgrounds, modworkshop `17160` → `Assets/`). `HOST_TARGETS` carries `host_mod_id`, `host_name`, `subpath`, a filename `signature` + `min_matches`, and `bundled` (set names the host ships itself, e.g. Menu Backgrounds' `"The Diamond"`). `detect_host_pack(names)` recognizes a pack by content signature (rejecting anything with a `mod.txt`/`main.xml` marker). A recorded pack's `InstalledMod.location` is `host:<id>:<subpath>`; `parse_host_location` / `host_target_by_id` read it back. The host's on-disk folder is always resolved from installed state by id, never assumed from its name. **Recovery after a state rebuild**: host packs live inside another mod, so the scan-target walk can't find them — `find_untracked_host_packs` (in `paths.rs`) scans the host's `subpath` (and the disabled area) for untracked set folders, excluding `bundled` defaults. `get_installed` then identifies each by its representative file's SHA256 against the index (`hashable_file_for_mod_dir` + `lookup_sha256`): a hit restores the real identity (`id` via `sources::source_native_local_id`, `remote_id`, name/version), a miss leaves an unidentified, folder-named entry whose stored sha256 lets a later index update upgrade it. **Modrex installs and tracks the files only — it never writes a host mod's own runtime/in-game settings to "activate" a pack** (e.g. Menu Backgrounds' `BGsSet` option is the user's to set in-game). Note: a host pack is only index-identifiable if its source mod is in `index.db` — e.g. a large RAR was unindexed until the `modrex-index` RAR/7z size cap was raised (a backfill run picks up the backlog).
    - `reorder.rs` — `reorder_mods_in_folder_op`, `move_mod_to_folder_op`, `reorder_children_op`
    - `folders.rs` — `create_folder_op` (idempotent: reuses an existing folder with the same `display_name` under the same `parent_id` instead of creating a duplicate record — callers that create folders in a loop, e.g. `ZipPickerModal`'s auto-folder-creation, can safely call it repeatedly for the same path without producing two state records that collide on one on-disk directory), `move_folder_op`, `rename_folder_op`, `delete_folder_op`
    - Key invariants:
        - `disabled_mod_path` appends `.disabled` to the `.pak` filename for File mods — the extension change is what disables mods (Unreal scans all subdirectories of `Paks/`, so subdirectory alone is insufficient). For Directory mods, disabling moves the folder into `disabled/`.
        - `get_installed` accepts `game_id: Option<String>` and uses `engine_for_game` to select the correct engine. All games are handled; there is no pd3-only guard.
        - `get_installed` identification pipeline: (1) SHA256-then-name index lookup upgrades entries with no `remote_id` yet; (2) name-suffix pass re-assigns identity to entries that still lack one; (3) untracked mods are auto-folder-created, reconciled by SHA256, then identified by hash → embedded modworkshop id → name (precedence detailed below). New untracked entries use `by_uid.entry().or_insert(...)` — existing entries are never overwritten. The command body is a thin orchestrator; each stage lives in a named helper: `upgrade_negative_ids`, `regroup_negative_ids_by_name_suffix`, `ensure_untracked_folders`, `hash_untracked`, and `identify_untracked` (Phase 1 SHA256 reconcile + Phase 2 identify, sharing one `sha256_to_uid` map). **Phase 2 precedence per mod**: exact SHA256 hit → **embedded modworkshop id** (Directory-unit mods only — `embedded_modworkshop_id` parses one format per BLT family, all verified against real downloads: BeardLib's `main.xml` `<AssetUpdates provider="modworkshop" id="N" version="V">`, RAID-SuperBLT's `supermod.xml` `<update provider="modworkshop" identifier="N">` with the version on the root `<mod>` element, and legacy RaidBLT's `mod.xml` `<auto_updates provider="modworkshop" id="N" version="V">`; enriched via `mod_index::query_mod_by_id`; preferred over the fuzzy name match because the embedded id survives version drift) → **name fallback** (`query_by_name` → numeric-stripped filename → `hash_filename`). `hashable_file_for_mod_dir` prefers `main.xml` → `supermod.xml` → `mod.xml` before the pak/first-file fallbacks, mirroring the indexer's `chooseMarker` so both sides hash the same representative file. **The marker-less fallback is a cross-language contract, not a coincidence**: both sides take the path whose UTF-8 bytes sort first, relative to the mod's own root, and the vectors live once in `apps/index/marker-contract.json` with a test on each side (`marker_contract_tests.rs` here, `pnpm test:marker-contract` there). A directory-by-directory walk is not the same ordering — it disagrees where a file and a folder share a stem — and neither is a locale-aware comparison, which is what made ModWorkshop 31190 (`vityaz_reload.animation` next to `vityaz_reload_not_empty.animation`) unidentifiable. Changing the ordering on one side alone strands every marker-less mod whose pick moves. An embedded-id mod's installed version is its own `main.xml` declaration, falling back to the index's current version so a drifted-old install reads as outdated rather than nagging a false "unknown" update. `upgrade_negative_ids` (renamed from `upgrade_negative_ids_by_sha`; the name predates `InstalledMod.id` becoming opaque for every source — it now gates on `m.remote_id.is_some()`, never `id`'s sign, and skips an already source-tracked entry, e.g. Nexus, outright rather than only checking `id >= 0`) tries SHA256 first, then falls back to `lookup_by_name(m.name)` on every miss — not just at first discovery. This matters because SHA256 misses permanently once a mod's modworkshop file is updated after install (the old installed bytes can never match a newer hash again); without the name retry, a mod that missed both checks once (e.g. because the local index happened to be stale at that exact moment) would stay "Unknown" forever, since this was previously the _only_ re-identification pass that runs on every refresh — the user would have had to wipe `.modrex.json` to force a fresh `identify_untracked` pass. On a hit it sets both `id` (via `sources::source_native_local_id("modworkshop", &remote_id)`) and `remote_id`, never just `id` alone, and the SHA256 branch must also move `update_status` to `Known`: the entry it is repairing was left `Unknown` by the pass that failed to identify it, and `useModData` skips an `Unknown` mod for updates forever, so a self-healed mod would silently never see an update again. Returns `bool` — both early-return paths (`mods_hidden` and `untracked.is_empty()`) check it and call `save_state` when true, so a recovered identity is never lost on the next write.
        - `install_mod` stores the **mod-level** version from `/mods/{id}` (not the file-level version from `/files/latest`). It inherits `folder_id` from existing state when the caller omits it.
        - **Multi-file installs**: `install_mod_from_path` finds `existing` by `uid` only (not `id`). `install_mod` pre-removes the old pak when exactly one same-id entry exists — never do this inside `install_mod_from_path`.
        - **ZIP installs**: `install_from_zip_entry` uid is `{file_id}_{entry_stem}`; SHA256 match reuses existing uid so reinstall moves in-place. `folder_id` is always caller-provided (never inherited from existing entries). `location_tag: Option<String>` param routes the install to the correct `ScanTarget`. Mirrors `install_mod`'s pre-removal via `stale_entry_for_zip_install`: when the resolved uid doesn't match any existing entry and exactly one other entry shares this mod id, that entry is uninstalled first — unless its uid starts with `{file_id}_`, i.e. it is an archive-scheme sibling of the file being installed right now: a multi-entry batch install (ZipPickerModal select-all) installs sequentially, so without that exclusion each entry saw exactly one same-id entry (the sibling installed a moment earlier) and deleted it, leaving only the last selected entry. The pre-removal exists because without it, a mod whose file packaging changes between a bare `.pak` (uid = `file_id`) and an archive (uid = `{file_id}_{entry_stem}`) leaves the old uid orphaned as a second tracked entry for the same mod, which also suppresses the update prompt (the dedup-by-id check in `useModData`'s `updatable` sees the new version already installed under the other uid).
        - `InstalledMod.uid` has `#[serde(default)]` so state files predating the uid field still deserialize
        - **Multi-target routing**: `cfg.target_for(m.location.as_deref())` is the canonical way to get a mod's `ScanTarget` in any op. Folder ops (`create_folder_op`, `move_folder_op`, etc.) always use `cfg.primary()` — app folders live only in the primary target's directory tree.

- **`launchers/`** — split into focused files so touching one launcher never requires touching another:
    - `types.rs` — `GameDef` struct (`name`, `executables`, `process_names`, `steam?`, `epic?`, `xbox?`), its `resolve_executable`/`is_installation` pair (see the split described under `mod.rs`), and the `Launcher` trait (`id`, `is_installed`, `find_game`, `identify_path`, `launch`)
    - `games/pd3.rs`, `games/pd2.rs` — one file per game; add new games as `games/<name>.rs`
    - `steam.rs` — Windows: `reg query` for install path, then walks `libraryfolders.vdf`; Linux: checks `STEAM_DIR`, `XDG_DATA_HOME`, snap, flatpak paths. `find_game` requires `is_installation` to hold for the candidate folder — a leftover folder without the game is not counted as installed. The Windows `reg query` result is cached in a `OnceLock<Option<String>>` for the process lifetime — never call `reg query` for Steam's install path outside this helper. The query runs through `run_bounded` (5 s).
    - `epic.rs` — reads `%PROGRAMDATA%\Epic\...\Manifests\*.item` JSON, then checks the manifest's `InstallLocation` with `is_installation`: a manifest outlives the install it describes, and an unchecked stale one used to win the probe order over a store that really had the game
    - `xbox.rs` — `find_in_drives` scans every subdirectory of each mounted drive root for `{dir}/{game.name}/Content/` containing the xbox executable; falls back to `find_via_package_manager` (PowerShell `Get-AppxPackage`, via `run_bounded` with a 15 s cap) for deeply nested installs; launches via `gamelaunchhelper.exe`. Xbox game path always ends in `/Content`. **`fixed_drive_roots` gate** (raw `GetLogicalDrives` + `GetDriveTypeW` externs — no windows crate dep; neither call does volume or network I/O): drives come from the live mount bitmask (A–Z, never a hardcoded letter list — a game drive on `H:` is a real setup) and only `DRIVE_FIXED` volumes are scanned, because the per-subdirectory stats block for the SMB redirector timeout on disconnected network/VPN drives and can stall on empty card readers — the cause of a real "Modrex is not responding" startup freeze — and Xbox installs only ever live on fixed NTFS volumes.
    - `mod.rs` — orchestration (`identify_launcher_for_path`, `launch_with`, `all_launchers`) + all Tauri commands. `game_def_for_id(game_id: &str) -> &'static GameDef` maps `"pd2"` to `&PD2`, `"pdth"` to `&PDTH`, `"cb"` to `&CRIMEBOSS`, `"raid"` to `&RAID`, anything else to `&PD3`. Marker files for `identify_launcher_for_path`: `steam_appid.txt`, `.egstore/`, `MicrosoftGame.config`. **Marker files are not universal** — a Steam PAYDAY 3 folder ships no `steam_appid.txt`, so this returns `manual` for it; never re-derive a launcher the user chose explicitly. `configure_game_path(None)` validates the existing saved path first (via `GameDef::is_installation`) and preserves the saved launcher as-is — it does not re-run `identify_launcher_for_path` on valid paths, because doing so clobbers games without marker files. **Which copy of the game to use is decided by `plan_resolution`, and it is the load-bearing part of this module.** Two stores' copies of one game are separate installs that share no files — each has its own mods folder and its own `.modrex.json` — so pointing at the wrong one makes an installed mod list read as empty. `Resolution` has four cases: `Keep` (settled copy still present — probes nothing, the steady state), `Refind(launcher)` (settled copy gone — probed under **that launcher only**, so a moved Steam library resolves while a copy that is merely mid-update reports missing instead of the game being handed to another store), `Missing` (settled on a hand-picked folder that is gone — nothing to probe), and `Settle` (not yet pinned — probe every store and choose via `pick_install`, which prefers the copy that already holds a `get_state_path` file). `install_pinned` is set by every write that resolves a copy, so `Settle` runs at most once per game; it is absent from settings files written before this existed, which is what makes an existing install re-choose once against the mod list on disk instead of staying on whichever store came first in the probe order. Never reintroduce a first-hit-wins detection order: a Steam copy installed after the fact used to take the game away from the Microsoft Store copy holding the mods, silently and permanently. **`GameDef::is_installation` vs `resolve_executable`**: the first answers "is the game here" and is what every recognition site must use (manual pick validation, saved-path revalidation, `Steam`/`Epic` `find_game`); the second answers "which executable do we spawn" and is launch-only. They differ because a Microsoft Store build has no Win64 bootstrapper at its root, only the nested WinGDK binary named by `XboxDef.executable` — validating a hand-picked Xbox folder against `executables` alone rejected a real installation. `select_game_install(game_id, launcher, game_path)` is how the Settings launcher picker switches between two stores' copies: it writes path and launcher together, taking the path from a `detected_installs` probe the renderer already ran so switching costs no new probing. `findGamePath()` in `api.ts` always calls `configure_game_path(null)` on every refresh — this is how stale paths (game uninstalled but folder left behind) get cleared. `is_game_running`, `launch_game`, `launch_without_mods`, `restore_mods`, `stop_game` all accept `game_id: Option<String>` and dispatch via `game_def_for_id` / `engine_for_game` — fully multi-game. The renderer passes `activeGame` to all five. The `-fileopenlog` warning in `TopBar` remains PD3-only (guarded by `activeGame === 'pd3'`). Private `do_restore(game_path, cfg)` is the shared restore implementation called by both `launch_game` (best-effort, errors ignored) and `restore_mods` (errors returned). `launch_game` calls it first so mods left in backup from a prior "launch without mods" session are restored before the game starts. Both `do_restore` and `launch_without_mods` iterate `cfg.targets` — each target gets its own backup dir; `base/` exclusion applies only to the primary target (index 0).
    - **Main-thread invariant**: sync Tauri commands run on the main thread, so a blocked probe freezes the window ("Modrex is not responding"). `auto_detect_game`, `detected_installs`, `configure_game_path`, `select_game_install`, and `is_game_running` are therefore `async` and run their work via `tauri::async_runtime::spawn_blocking` — never convert them back to sync, and route any new detection command through the same pattern. Detection subprocesses (`reg query`, `Get-AppxPackage`) go through `run_bounded` (in `mod.rs`), which polls with a deadline and kills the child instead of `.output()`'s unbounded wait — the same lesson as the old tasklist/WMI freeze fix, now applied to every probe. `run_bounded` sets `CREATE_NO_WINDOW` and pipes stdout itself; it reads stdout only after exit, so it's only suitable for small-output commands (single-line results). Both `detect_game` and `detected_installs` gate each store on `is_installed()` before probing and log `probing <launcher> for <game>` before each `find_game` — the last such line in `Modrex.log` pinpoints a hung probe, which is otherwise traceless. `detect_game` stops at the first hit (one path is all settings can hold); `detected_installs` collects every store's copy, because a game owned twice has two real installations and the launcher picker switches between them.
    - **Windows `CREATE_NO_WINDOW` invariant**: The release binary sets `windows_subsystem = "windows"` (`main.rs:1`), so it has no console. Any `std::process::Command` on Windows without `creation_flags(0x08000000)` spawns a visible console window. In debug builds (`pnpm dev`) this is invisible because the process inherits the parent console. Every spawn of a **console-mode executable** (cmd, tasklist, PowerShell, cargo, pkill, pgrep) must use `use std::os::windows::process::CommandExt` and `.creation_flags(0x08000000)`. GUI shell programs (`explorer.exe`, `xdg-open`) are exempt — they never attach to a console regardless.

- **`loaders.rs`** — the mod-loader registry: `LoaderSpec { id, modworkshop_ids, games, detect, install }` and `LOADER_REGISTRY`. A loader is a hook installed next to the game, never tracked in `state.json` and never uninstallable through Modrex, so the five differ only in detection and layout — both captured as data. `DetectStrategy::RootFiles(&[...])` covers SuperBLT (`WSOCK32.dll` current / `IPHLPAPI.dll` legacy / `libsuperblt_loader.so` Linux native, PD2 only), PDTHModOverrides (`DINPUT8.dll` is the proxy and the sole signal; `PDTHModOverrides.dll` is the payload and is installed but not detected), DAHM (`lightfx.dll`), and RAID-SuperBLT (`WSOCK32.dll`/`IPHLPAPI.dll`, no `.so` — RAID has no native Linux build; `IPHLPAPI.dll` may also be the discontinued RaidBLT). `DetectStrategy::Ue4ssProxy` delegates to `ue4ss.rs`, whose proxy DLL and destination vary per `(game_id, launcher)`. `InstallStrategy` is `ExtractEntries` (SuperBLT pulls only `WSOCK32.dll` — the BLT basemod is fetched by the loader itself on next launch; PDTHModOverrides pulls both DLLs), `ExtractAllFlat` (DAHM and RAID-SuperBLT ship framework modules / the Lua basemod inside, so the whole archive lands in the game root), or `ViaModFlow` (UE4SS has no canonical host — each release is a modworkshop mod page, so installs route through the normal mod flow via `zip.rs`'s `UE4SS_LOADER` sentinel). Commands: `list_loaders` (hands the registry to the renderer, which maps dependency ids to loaders instead of restating the tables), `check_loader`, `install_loader` — an unknown loader id is a hard error. `modworkshop_ids` is empty only for SuperBLT, which has no mod page and is matched by the renderer's `blt` name heuristic instead.

- **`superblt.rs`** — only `is_pd2_diesel3` remains: the Diesel 3.0 branch ships no SuperBLT build, so a present loader still counts as unusable there. SuperBLT's own detect/install data lives in `loaders.rs`.
- **`updater.rs`** — auto-update flow via `tauri-plugin-updater`. `UpdaterState` (managed Tauri state) holds the pending `Update` object and its downloaded bytes across two separate commands. Three-phase sequence: `check_for_update` fetches metadata and stores the `Update` object, emitting `updater:update-available`; `download_update` streams bytes and emits `updater:update-progress` (percent) then `updater:update-ready`; `install_update` takes both and applies. Strategy is always `"manual"` — there is no auto-install path.

- **`thumbnails.rs`** — Thumbnail disk cache. `get_thumbnail(filename)` checks `app_cache_dir()/thumbnails/thumbnail_{filename}`, downloads from `https://storage.modworkshop.net/mods/images` if absent (6-slot semaphore, atomic write via `.tmp` rename), and returns the **cache filename** (not a path) for the renderer to build its `thumb://` URL. By default it downloads the pre-generated `thumbnail_{file}` CDN variant, falling back to the original for old images with `has_thumb: false`; with `full: true` it caches the original under `{filename}`. **Variant policy**: the small variant is only **256 px wide** and upscales badly — use it solely for renders ≤ ~120 px (`ModListRow`'s `w-28` thumb, `DependencyRow`'s 40 px icon); everything wider (`ModCard`, gallery tiles, banner, lightbox) must use `full: true`. The CDN sends no cache headers, so direct CDN URLs cost a download or revalidation round-trip per view — always go through this cache. `cleanup_thumbnail_cache` runs fire-and-forget at startup and removes files whose `modified()` time exceeds 90 days. The modworkshop CDN sends no `Cache-Control` header (`cf-cache-status: DYNAMIC`), so without this every app launch revalidates images over the network. `handle_thumb_protocol` backs the custom `thumb://` URI scheme (registered in `lib.rs`): it serves files from the thumbnails cache dir with `Cache-Control: public, max-age=31536000, immutable`. `sanitize_thumb_filename` percent-decodes the URI path and rejects separators/`..` — every request must pass it before touching the filesystem (path-traversal guard; unit-tested).

- **`mods/identity.rs` + `mods/diesel_signals.rs`** — **what an installed mod _is_, separately from where it can be downloaded.** `ModIdentity { namespace, key, evidence, confidence }` on `InstalledMod` answers "which project is this"; `source`/`remote_id` continue to answer "and which catalog entry does it correspond to". The two are independent: a mod distributed only from its author's own updater gets a real identity and no catalog link, and the renderer's `isIdentified`/`hasCatalogLink` split mirrors that. **`namespace` is a field, never a prefix parsed out of `key`** (`modworkshop`+`25629`, `pd2mods.z77.fr`+`Celer`, `github`+`owner/repo#Declared Name`, `paydaymods`+`silentassassin`), so two ecosystems cannot collide and no consumer has to know the key's shape; a namespace implies nothing about capability. `confidence` is derived from `evidence` by the single constructor and is never read back from disk, so the two cannot disagree.

    **The operation that establishes a catalog association records the evidence for it, in the same statement.** `InstalledMod::attach_catalog` / `from_catalog` (types.rs) write `source`, `remote_id`, the derived `id` and the identity together; nothing reconstructs provenance afterwards, and in particular `update_status` carries no identification history. What each path records: install → `InstallProvenance`; SHA256 index hit and Nexus MD5 archive match → `CatalogHash`; validated embedded BeardLib id → `EmbeddedCatalogId`; Nexus content lookup (published file name + size, or content folder segment) → `CatalogContentMatch`; index name match or a filename that is itself an id → `CatalogName`. `CatalogReference` means only "an older state file already carried this reference and how it was found was never recorded" — never claim an install that is not known to have happened.

    `resolve_identity` is pure, offline, and covers only mods with no catalog association: embedded catalog id → updater namespace → repository plus declared name → legacy namespace → name+author (`Candidate`, a guess that never counts as identified). `ensure_identities` fills the remainder from `get_installed` at all three exits and never recomputes an identity that is already recorded — a recorded identity describes the folder as of the scan that recorded it, exactly like `name`, `version` and `sha256` on the same record. Changing the extraction rules in a later release therefore needs a deliberate one-time clear of locally derived identities, not a rescan.

    The generic model knows nothing about mod files. `SignalSource` on `ModEngineConfig` says which vocabulary a game's mods speak (`Diesel` for PD2/PDTH/RAID, `None` for the pak games), and `diesel_signals.rs` owns every BLT and BeardLib rule, each of them forced by the ecosystem rather than chosen: `mod.txt` is scanned rather than parsed because 7.5% of shipped files are not valid JSON; a `simple_update_url` outranks the `updates` block because a whole family of mods declares the identifier of the _updater tool_ they share (twelve distinct mods collapse onto one key otherwise); a repository is never an identity on its own since surveyed repositories hold up to 130 mods; an `updates` entry with no host is a paydaymods.com record, dead since February 2020, kept namespaced for recognition with no update capability implied; and an `AssetUpdates` id is validated against the snapshot before it is trusted, because a third of them are template placeholders and at least one real mod ships another project's id.

- **`mod_index.rs`** — SHA256-based mod identification against per-game SQLite snapshots published to R2. `ensure_index` (fire-and-forget from the `lib.rs` setup hook) reads the catalog manifest at `https://index.modrex.net/catalog/latest.json` and refreshes each game with a valid saved path: the snapshot downloads to `app_data_dir()/indexes/<game_id>.db`, skipped when the sha256 recorded beside it in `indexes/<game_id>.json` already matches the manifest, and every download is verified against the manifest size and sha256 before an atomic `.tmp`-then-rename write. Snapshots keep the schema `games`, `sources`, `mods`, `files`, so the query layer is unchanged from the monolithic era. The frozen `modrexio/modrex-index` release serves only desktop versions through 0.12.2 and is never written from this repo. `query_sha256(conn, sha256, game_name)`, `query_by_name(conn, name, game_name)`, and `query_mod_by_id(conn, mod_remote_id, game_name)` (newest indexed file for a known modworkshop id, used to enrich embedded-id matches) are private helpers that take a `&rusqlite::Connection`, testable with in-memory SQLite. All three join `files` to `mods` to `sources` to `games` and filter by `games.name = game_name` so a PD2 hash never matches a PD3 mod. `lookup_sha256(app, sha256, game_id, game_name)` is the public wrapper; callers pass `cfg.game_id` and `cfg.index_game_name`. `open_index(app, game_id)` opens the per-game db once, falling back to the legacy monolithic `mod-index.db` when absent, so a caller can run several queries against one connection: `upgrade_negative_ids` and `identify_untracked` both use it instead of reopening per lookup (`get_installed` is a hot path: startup, window focus, path changes). Both name-matching callers try the folder-derived name first and then the name the mod declares in its own `mod.txt` (`identify.rs::declared_mod_name`, Directory-unit targets only). The folder is whatever the archive unwrapped to, which for a GitHub source zip is the repository plus branch (`PD2-DiscordRichPresence-main`) and matches no mod page, while the declaration is the title the author publishes under. Measured against the reporter's real 31-mod install: 3 more mods identified, 0 wrong, and the one genuinely ambiguous declaration (`Silent Assassin`) still refused. It is strictly additive — a folder-name hit is never overridden, since a declaration can also be _worse_ (`VanillaHUDPlus`, no spaces, matches nothing). `query_by_name` returns `Some` only when exactly one mod matches (ambiguous = `None`) **and** that one match falls on a word boundary. LIKE has no notion of a word, so a folder named `Bag Contour` matched the unrelated mod `Blue Bodybag Contour` and took its identity — measured against two real installs, the boundary rule removes exactly that case and keeps every legitimate partial match (`Useful Bots` → `Useful Bots: Future Edition`, `Ammo Pickup Amount in HUD` → `Show Ammo Pickup Amount in HUD`). It is deliberately subtractive: it is applied to the single surviving candidate, never used to pick between several, so an ambiguous set stays refused rather than being resolved onto a mod the guard was already rejecting. **`files.remote_id` (and therefore `InstalledMod.file_id`) is positive for a ModWorkshop file and negative for a ModWorkshop link** — see `apps/index/CLAUDE.md`; a mod whose page only links off-site has no file id to carry, and the two id spaces overlap, so the sign is what keeps `findSuspectDuplicateGroups`' game-wide grouping by file id sound. Uses `rusqlite` with `features = ["bundled"]`.

- **`news.rs`** — scrapes `paydaythegame.com`'s per-game news category page (`category_slug`: `"pd2"` → `payday2`, `"pdth"` → `theheist`, else `payday3`) for the News tab. **Fetches via a `curl` subprocess, not `reqwest`**: the site's Cloudflare bot management 403s every library HTTP client tried (`reqwest`, .NET `HttpClient`) regardless of headers — a TLS/HTTP2 fingerprint check — and a renderer-side `fetch()` is blocked too since the site sends no `Access-Control-Allow-Origin` header; `curl.exe` is the one client that passes (verified live), so `curl_fetch` shells out to it with `creation_flags(0x08000000)` on Windows, matching the `reg query`/`powershell` subprocess pattern in `launchers/`. `parse_news_html` (pure, HTML-in/`Vec<NewsItem>`-out) and `extract_total_pages` (parses the WP-PageNavi block — the total is the max page number across every `.wp-pagenavi a` link plus the `.current` span, since WP-PageNavi omits the link to whichever page you're already on) are both unit-tested against saved fixtures. `fetch_news`/`refresh_news` (page 1 only) are TTL-cached to `app_data_dir()/news-{slug}.json` (1 hour, same atomic `.tmp`-then-rename write as `mod_index.rs`); `fetch_news_page(game_id, page)` fetches any other page uncached. All three return `NewsResult { items, total_pages }`.

- **`storage.rs`** — backs the Settings > Storage section. `get_storage_usage` reports on-disk sizes of the thumbnails cache (`app_cache_dir()/thumbnails`), `mod-index.db`, and the `news-*.json` caches — the renderer's localStorage mod-metadata cache is sized/cleared on its own side (`modCache.ts`), since Rust can't see localStorage. `clear_thumbnail_cache` / `clear_index_cache` / `clear_news_cache` delete each and return the bytes freed, leaving the containing directory in place so the cache refills; `remove_file_freed` tolerates a live handle (returns 0 rather than erroring, e.g. mod-index.db mid-query on Windows). `dir_size`/`remove_files_in` are flat, files-only helpers matching `thumbnails::cleanup_dir`'s flat-cache assumption. The destructive counterpart is `settings.rs`'s `reset_app_settings`.

- **`analytics.rs`** — anonymous, opt-in GA4 usage telemetry via the Measurement Protocol, sent from Rust. See the **Usage analytics** section below for the full design.
