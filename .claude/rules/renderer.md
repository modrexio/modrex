### Renderer (`src/renderer/src/`)

Paths in this rule are relative to `apps/desktop` unless they already start with
`apps/desktop`.

**`api.ts`** — the only renderer file that talks to the IPC layer: it calls the generated `commands.*` functions from `src/shared/bindings.ts` (which owns the raw `invoke` strings) plus `listen`. All other renderer code imports from here — never from the bindings directly (check-commands enforces both). The bindings are generated from lib.rs's `ipc_builder()` registry by the `export_bindings` Rust test; never edit them by hand. Generated optional params are `T | null` — wrappers pass `x ?? null` and keep their public `?:` signatures. Mod data is typed end to end: `listMods`, `getMod`, `listModFiles`, `listModLinks` and `nexusSearchMods` are assigned to the hand-written types in `src/shared/types.ts` **without a cast**, so any drift from the generated shapes is a compile error in this file. Only the few genuinely untyped passthroughs still return `unknown` and are cast. `onEvent<T>` wraps `listen` with a cancellation-safe pattern (resolves the `UnlistenFn` async, cancels immediately if component unmounts first). Every game-scoped wrapper takes a **required** `gameId: string` — there is no pd3 default any more: an unknown or absent game id is a hard command error on the Rust side, per the game registry (`commands/games.rs`). Always pass `activeGame` from context. `installFromZipEntry(..., gamePath, gameId, folderId?, locationTag?, entryKind?)` and `installDroppedFile(path, gamePath, gameId, folderId?)` put the required `gameId` before their optional trailing params; pass `payload.targetTag` as `locationTag` from `ZipMultiPakPayload`.

**`App.tsx`** — owns `installed`, `gamePath`, `modsHidden`, `activeGame` as sources of truth. `detailStack` is `{ modId: number; initialMod?: ModSummary }[]` — each entry carries the optional browse-list summary so `ModDetailPage` can render the header instantly before the full fetch completes. It is a `ModSummary`, not a `Mod`: a browse list cannot supply detail fields, and the type now says so. `openDetail(modId, from, initialMod?)` resets the stack to a single entry; `pushDetail(modId)` appends (or truncates to an existing entry) without an `initialMod`. `View` type includes `'welcome'` in addition to the nav views. **There is no `'nexus'` view any more** — Nexus moved into Browse behind the source switcher, and a saved `'nexus'` view falls back to Browse. Which source Browse shows is `browseSource` state, persisted per game under `modrex:{storageKey}:browse-source` and reset to modworkshop whenever the saved source is not one that game offers. `getInitialView()` returns `'welcome'` when `modrex:active-game` is absent from localStorage (first launch). `activeGame` initializer reads localStorage and accepts any valid `GameId` via the `isGameId` guard (derived from `GAME_SPECS`, so a new game needs no edit here) — never assume it defaults to `pd3`. `handleGameChange(g)` restores `gamePath` from `gamePathCache` and `installed`/`folders`/`modsHidden` from `installedCache` (so the UI never flashes "game not found" or "no mods installed" while re-validation runs in the background), saves the game to localStorage, and navigates to the saved nav view — all state updates wrapped in `startTransition`, because the switch commit renders three pages' worth of tree at once and a transition keeps it interruptible (rapid switching cancels the in-progress render instead of queueing jank). Falls back to empty state when a game has never been loaded this session. Installed readiness is per-game: `readyGames: ReadonlySet<GameId>` holds the games whose installed list has been fetched at least once this session. The startup splash shows while the set is empty; `InstalledPage` receives `installedReady={readyGames.has(activeGame)}` so the first fetch for each game shows "Loading…" instead of a false "No mods installed yet". `handleShowWelcome()` navigates back to the welcome screen. When `view === 'welcome'` the entire TopBar/Sidebar is hidden — only `WelcomeScreen` renders inside the root div. App version shown in `TopBar.tsx` comes from `import.meta.env.VITE_APP_VERSION`, injected by Vite's `define` in `vite.config.ts` from `package.json` at build time; shows `v-dev` in dev mode. `TopBar` receives `activeGame: GameId` — its pre-launch warning fires only when the game's `requiredLaunchFlag` spec field is set and missing from the saved launch options, and `SettingsPage` shows its launch-options hint and placeholder from the same field, so both are automatically silent for games that need no flag (today only PD3 does, with `-fileopenlog`). On startup, on every window focus (500ms debounce), and after a manual path change (`SettingsPage`'s `onGamePathChange`), `refreshAll` runs — it awaits `refreshGamePath` before `refreshInstalled`, because `get_installed` reads the game path from settings and a concurrent fetch can return a false-empty list before path detection has persisted. All nav pages (and detail-stack entries) stay mounted as `absolute inset-0` panes inside the `relative` `<main>`, toggled with `invisible pointer-events-none` — **never `hidden`/`display:none`**: un-hiding a `display:none` subtree re-layouts it from scratch and re-decodes every image, which made tab switches stutter; a visibility flip is paint-only and preserves layout, decoded images, and scroll. `BrowsePage` is wrapped in `memo` with stable callbacks (`openDetailFromBrowse`, `goToSettings`) so hidden re-renders are skipped, and receives `isActive={view === 'browse'}`: its fetch effect no-ops while inactive and re-runs the SWR check (`browseCache.ts`: show cached, background re-fetch if stale) on activation; scroll resets only on filter changes, so position survives tab switches. It still remounts on game change via `key={activeGame}`. Inside `BrowsePage`, the card grid is a `memo` boundary (`ModGrid` → per-card `GridCard`): the grid re-renders only when its data props change — never on `isActive` flips, search keystrokes, or modal/error state — and a grid re-render (e.g. download progress) re-renders only the affected card. All handler props crossing that boundary must stay `useCallback`-stable or the memo is defeated. `refreshInstalled` short-circuits (no state updates) when the fetched result deep-equals the `installedCache` entry — focus refreshes usually change nothing, and the fresh array refs would otherwise re-render the installed list and browse grid on every refocus. `SettingsPage` uses `key={activeGame}` to force a full remount on game change, ensuring stale per-game state (launcher, paths) never bleeds through.

**`activeGameRef`** — a `useRef<GameId>` kept in sync with `activeGame` via `useLayoutEffect`. Used by `refreshGamePath` and `refreshInstalled` to discard results that arrived after a game switch. **Must be updated via `useLayoutEffect`, never during the render body** — the `react-hooks/refs` ESLint rule enforces this; writing to a ref in the render body is an error caught by the pre-commit hook.

**`isRefreshingInstalled`** — a `useRef<boolean>` declared alongside `activeGameRef` and reset to `false` in the same `useLayoutEffect` on game switch. `refreshInstalled` checks it at entry and returns early if `true`, then sets it `true` for the duration of the Tauri call and clears it in `finally`. Prevents two concurrent `get_installed` invocations (focus debounce + manual refresh) from racing `save_state` and overwriting positive IDs with negatives.

**`gamePathCache`** — a `useRef<Partial<Record<GameId, string | null>>>({})` that stores the last resolved path for each game per session. `refreshGamePath` writes to it after every successful `findGamePath` call. `handleGameChange` reads from it to restore the previous path immediately, preventing the "game not found" flash while the background re-validation completes. `undefined` means the game was never resolved this session; `null` means it was resolved but not found.

**Failed-detection throttle** — `failedDetectAt` (a ref in `App.tsx`) records when detection returned "not found" per game; `refreshGamePath` skips re-detection for `DETECT_RETRY_MS` (5 min) after a failure, because re-detecting a missing game runs the full launcher scan on every switch/focus otherwise. `SettingsPage`'s `onGamePathChange` is wired to `handleGamePathSet`, which clears the marker before refreshing — a manual path pick must bypass the throttle.

**`gamePathReady`** — a boolean state in `App.tsx` that is `false` while the active game's path is still being resolved this session (auto-detection can take seconds — Steam VDF walk, Epic manifests, Xbox drive scan). Set `true` by `refreshGamePath` on completion; `handleGameChange` sets it from `gamePathCache` presence (`cachedPath !== undefined`). Passed to `BrowsePage` and `SettingsPage`, which must never render a definitive negative ("Game not found" banner, red "could not detect" text) until it is `true` — while `false`, `BrowsePage` renders nothing and `SettingsPage` shows a neutral "Detecting…" placeholder. Components that only disable actions on a falsy `gamePath` (`TopBar`, install buttons) don't need it.

**`installedCache`** — a `useRef<Partial<Record<GameId, { mods, folders, modsHidden }>>>({})` that mirrors `gamePathCache` for installed mod state. `refreshInstalled` writes to it after every successful fetch. `handleGameChange` reads from it to restore the previous installed list immediately, preventing the "no mods installed yet" flash on the Installed page while the background re-validation completes. `undefined` entry means the game was never loaded this session — falls back to the empty reset.

**`WelcomeScreen.tsx`** — full-screen game picker shown on first launch and when the user clicks the game switcher in the sidebar. Banner images load from Steam CDN (`cdn.akamai.steamstatic.com/steam/apps/{appid}/library_600x900.jpg`) with a per-game gradient fallback on `onError`. Selecting a game calls `onSelectGame(g: GameId)` which is wired to `handleGameChange` in `App.tsx`.

**`Sidebar.tsx`** — game switcher is an `ArrowLeftRight` + full game name button at the top; clicking calls `onShowWelcome`. No game-selection logic lives in the sidebar itself. A "Documentation" button (`CircleHelp` icon) sits above the collapse button and calls `api.openExternal` to open `https://modrex.net/docs/` in the system browser.

**`modCache.ts`** — 5-minute in-memory TTL cache for mods, files, and links; all three are persisted to localStorage (24-hour shelf life) under `modrex:mod-cache`, `modrex:files-cache`, `modrex:links-cache`. On module init, `loadFromStorage()` pre-warms all three Maps from localStorage. Writes are debounced 2 s via `scheduleStorage()` which flushes all three keys in one pass. Always use `getCachedMod` / `getCachedModFiles` / `getCachedModLinks` — never call `api.getMod`, `api.listModFiles`, or `api.listModLinks` directly. Three synchronous accessors return cached entries without fetching: `getModCacheEntry(id)` returns `{ mod, fetchedAt }`; `getFilesCacheEntry(id)` returns `{ files, fetchedAt }`; `getLinksCacheEntry(id)` returns `{ links, fetchedAt }`. These are used by `ModDetailPage` to sync-initialize state on mount, bypassing the loading spinner when data is already warm.

**`nexusModCache.ts`** — Nexus's own cache module, deliberately separate from `modCache.ts` rather than merged into it: Nexus mod ids are only unique within a game domain (they repeat across games) and can also collide numerically with a modworkshop id, so every entry is keyed `${gameId}:${modId}`. Session-only, no localStorage persistence. `getCachedNexusMod`/`getCachedNexusModFiles` (5-minute TTL) back the Nexus mod detail page, mirroring `modCache.ts`'s per-id accessors; `getNexusModCacheEntry`/`getNexusFilesCacheEntry` are the matching sync accessors. `fetchInstalledNexusModsMeta(gameId, modIds, onResult?)` is the Nexus half of `useModData`'s update check — Nexus has no batch metadata endpoint, so it fetches one mod at a time (`STAGGER_MS` = 2 s between requests, on top of `waitForForegroundClear()`) against an undocumented hourly quota, writing into its own `installedMetaCache` (same long TTL as modworkshop's, to stay in lockstep with `useModData`'s staleness check) rather than the 5-minute detail-page cache above. `onResult` fires after each mod resolves, not just once the whole trickle finishes, so the UI can update incrementally instead of waiting for a potentially large installed list to finish one at a time.

**A fourth, deliberately separate cache** — `installedMetaCache` (`INSTALLED_META_TTL_MS`, 30 min, exported so `useModData`'s own staleness check stays in lockstep; persisted under `modrex:installed-meta-cache` alongside the other three) — backs `fetchInstalledModsMeta(workshopId, ids)`, which bulk-refreshes installed-mod metadata via the `ids[]` listing filter (chunked ~50 ids per call, see `api.rs`) instead of one `get_mod` per id. **Invariant: entries here must never reach `modCache`.** The `ids[]` filter returns the list-item shape — missing `images`/`dependencies`/`changelog`/full `banner` — and `ModDetailPage` seeds from `getModCacheEntry` treating any hit as complete (skips re-fetching for the TTL window), so a thin entry leaking into `modCache` would silently render a broken detail page (no gallery, no dependency warnings) until the cache expired. `fetchInstalledModsMeta` unconditionally fetches and caches whatever ids it's given — the caller (`useModData`) decides what's stale, mirroring the per-id functions' division of labor above. Ids missing from the response (deleted mods) come back in `failedIds`. Each chunk awaits `waitForForegroundClear()` (`requestPriority.ts`) first, so this silent bulk refresh yields to whatever the user is actively waiting on. `getInstalledMetaEntry(id)` is the sync accessor, used the same way as the three above.

**`requestPriority.ts`** — lets background API work defer to foreground work so it doesn't sit queued behind silent background calls on the shared rate-limited connection to modworkshop. `markForegroundActivity()` (called by `BrowsePage.fetchMods` and `ModDetailPage.fetchData`, at both start and completion) and `waitForForegroundClear()` (awaited by `modCache.ts`'s `fetchInstalledModsMeta` before each chunk, and by `BrowsePage`'s hover-prefetch before firing) track **recency of foreground activity** — a single `lastForegroundAt` timestamp — rather than an in-flight counter, deliberately: a call site that forgets to mark completion can't permanently starve background work, since at worst `waitForForegroundClear` just waits out one 1.5 s quiet window and proceeds anyway. The "never marked" sentinel is `-Infinity`, not `0` — `0` collided with tests that fake the clock to epoch 0, reading as "foreground just active" and hanging forever on a timer that never advances (caught by `requestPriority.test.ts`).

**`BrowsePage.tsx`** — `fetchMods` calls `markForegroundActivity()` around the `api.listMods` call (start and `finally`) so the installed-mod bulk refresh and hover-prefetch yield to it. `handlePrefetch` (the 150 ms hover-debounced `getCachedMod`/`getCachedModFiles`/`getCachedModLinks` prefetch) awaits `waitForForegroundClear()` before firing. On a fetch failure, `isRateLimitError(error)` matches the literal `"API 429"` substring `api.rs`'s `api_get` produces (not just `"429"`, so a mod id containing 429 inside some other error's path never false-positives) and selects a friendly amber notice (`t('browse.rateLimited')`) instead of the raw error string; whatever `result` is already cached (even stale) keeps rendering underneath either way, since `getBrowseCache` returns stale entries rather than evicting them. `ModGrid`'s skeleton branch is gated on `loadingMods` alone — a separate `!result` branch (`t('browse.loadFailed')`) covers a cold start with nothing cached where the fetch failed, which previously fell through to the skeleton branch and rendered placeholder cards forever.

**`NewsPage.tsx`** — News tab. A module-level `Map<GameId, { items, totalPages, page }>` caches the last-viewed page per game for the session (mirroring `gamePathCache`'s pattern) so switching tabs or games restores where the user left off instead of resetting to page 1. Pagination is deliberately a clone of `BrowsePage`'s numbered-page footer (`buildPages`, same active-page styling) rather than infinite scroll, to match the rest of the app: the clicked page number updates `page` state _before_ the fetch resolves (so the highlight is instant), and the previous `items`/`totalPages` are kept on screen (grid swaps to skeletons, footer never unmounts) while the new page loads — clearing them on click would hide the footer mid-transition, the opposite of `BrowsePage`'s behavior. Article links open via `api.openExternal`, never raw `<a href>`.

**`thumbnailCache.ts`** — Persistent thumbnail cache bridge. Module-level `resolved: Map<filename, thumbUrl>` deduplicates IPC calls within a session. `getLocalThumbnail(filename)` invokes `get_thumbnail` (which ensures the file exists in the disk cache, downloading if missing), then builds the URL via `convertFileSrc(filename, 'thumb')` — the custom `thumb://` protocol registered in `lib.rs`, **not** Tauri's asset protocol. The thumb protocol serves files from the thumbnails cache dir with `Cache-Control: immutable` (CDN filenames are content-unique), so the webview reuses cached decoded images across page remounts — the asset protocol sends no cache headers, which made every game/tab switch re-decode the whole grid. The `thumb:`/`http://thumb.localhost` origins must stay in `img-src` in both `csp` and `devCsp`. `getCachedThumbnailUrl(filename)` is a synchronous accessor used by `useThumbnail` to initialize state without triggering an IPC call on second render. Never call `api.getThumbnail` directly — always go through `thumbnailCache.ts`. `useModData` pre-warms thumbnails for all installed mods as mod data becomes available (both the sync cache pass and the async fetch pass).

**`hooks/useThumbnail.ts`** — Hook for thumbnail images. Initializes state synchronously from `getCachedThumbnailUrl` (local asset URL if already resolved this session); otherwise races `getLocalThumbnail` against a 50 ms timeout. A disk-cache hit wins the race, so the CDN is never touched; on timeout the CDN URL is shown **and kept for that mount** — never swap `src` after the CDN image may have painted, because the swap makes the webview re-load the image (visible flicker). The resolved local URL is still recorded so future mounts resolve synchronously. Consumers must render a placeholder for a `null` src (covers the sub-50 ms race window). The optional `full` param selects the original image instead of the 256 px small variant — see the variant policy in the `thumbnails.rs` section for which renders need which. Used in `ModCard` (full), `ModListRow` (small), and `ModDetailPage` (banner/`GalleryImage`/`LightboxImage` full, `DependencyRow` small) — never use a bare CDN URL for thumbnails. The one deliberate exception: user avatars in `ModDetailPage`'s members section load straight from `AVATAR_BASE_URL` (`users/images` on the storage CDN, `thumbnail_` prefix when `avatar_has_thumb`) — the disk cache and `thumb://` protocol only serve mod images (`mods/images`), and avatars are too small/rare to justify extending it.

**`settingsCache.ts`** — session cache for SettingsPage data: `Map<GameId, { settings: GameSettings, installs: DetectedInstall[] }>`, mirroring `gamePathCache`/`installedCache`. `installs` holds every store's copy of the game with its path, which is what lets the launcher picker switch copies without re-probing; a game owned on two stores has two entries and `handleLauncherChange` sends the chosen one's path to `select_game_install`, then refreshes through `onGamePathChange`. Selecting a launcher must never write the launcher alone — that leaves Modrex modding one copy and launching the other, which is why `set_launcher` no longer exists. `effectiveLauncher` is display-only and never writes back: a copy that is mid-update is missing from `installs` while still being the copy in use, so the saved launcher is shown as saved and added to the options list when no probe reports it. `warmSettingsCache(game)` in `App.tsx` prefetches it whenever `activeGame` changes (and at startup), so the cache is warm before the user can reach the Settings page. `SettingsPage` sync-initializes its state from `getSettingsCache(activeGame)` in its `useState` initializers (safe because the page remounts per game via `key={activeGame}`) and revalidates in the background via `setSettingsCache`. **Render-once rule**: while `settings === null` (cold cache, prefetch not yet landed) the page renders `null` — a sub-100 ms blank reads as instant, whereas rendering provisional values that then flip reads as a glitch. The one exception is the game path, which can take seconds to detect: it shows an explicit "Detecting…" spinner placeholder (placeholder → value is acceptable; value → different value is not). **Mutation invariant**: every user mutation on the page (launcher select, debounced launch-options save, manual path pick) must call `patchSettingsCache` — otherwise the next remount restores pre-mutation values until the revalidate lands. The background revalidate only refetches `get_game_settings` (cheap settings.json read); `installed_launchers` (slow registry/manifest probe, changes only if the user installs a launcher mid-session) is reused from the session cache once warm.

**`StorageSettings.tsx`** — the Settings > Storage card (Advanced tab, below Logs). A flat `danger`-token "danger zone" card (no gradients/decoration — matches the app's `bg-warning/10 border-warning/30` warning-banner treatment) with one row per cache showing its live size and an explicit clear button (Clear images / mod info / database / news), an "All caches" row, and a "Reset settings" row. **Every** delete routes through one shared confirm dialog (a `ConfirmSpec` state object drives the single `Dialog`) so nothing deletes on one click. Sizes come from `api.getStorageUsage` (disk) plus `getModCacheSize()` (localStorage); each clear reports freed bytes inline in `text-success-text`. Clearing dispatches to the `storage.rs` commands, `clearModCache()` (mod info), and `clearResolvedThumbnails()` (drops the in-memory thumbnail-URL map so cleared images re-download); "Reset settings" calls `api.resetAppSettings`, wipes all `modrex:` localStorage keys, and reloads. `modCache.ts` gained `getModCacheSize()` (byte estimate of the four persisted caches) and `clearModCache()` (wipes the in-memory maps + their localStorage keys, cancelling the pending debounced write first so it can't re-persist); `thumbnailCache.ts` gained `clearResolvedThumbnails()`.

**`browseCache.ts`** — in-memory SWR cache for the Browse page. Keyed by `(workshopId, page, query, sort, categoryId, includeTags, excludeTags)` — the two tag-id sets are sorted and joined into the key so a tag-filtered page never collides with the same unfiltered page; the `workshopId` prefix is load-bearing: without it, switching games pollutes the other game's cache. `getBrowseCache`/`setBrowseCache` take the include/exclude tag arrays as trailing params (default `[]`). All exported functions (`getBrowseCache`, `setBrowseCache`, `getCategoriesCache`, `setCategoriesCache`, `getTagsCache`, `setTagsCache`) take `workshopId: number` as their first argument. 5-minute TTL for mod list pages; 1-hour TTL for categories and tags. `getBrowseCache` returns `{ result, stale }` or `null` — callers show the cached result immediately and skip or background-fetch based on `stale`. `categoriesCache` and `tagsCache` are each a `Map<workshopId, {..., fetchedAt}>` — one entry per game, not a singleton. Not persisted to localStorage (lives only for the process lifetime). `BrowsePage` reads the initial cache synchronously during component init so the first render already has data on return visits.

**Browse tag filter** — `TagFilter.tsx` (a `@radix-ui/react-popover` dropdown, one row per tag cycling neutral -> include -> exclude, 10 per bucket) drives `includeTags`/`excludeTags` state in `BrowsePage`, threaded through `fetchMods` into `api.listMods`'s `tags`/`block_tags` and into the browse-cache key above. The tag catalog comes from `api.listTags(workshopId)` cached via `getTagsCache`/`setTagsCache`, fetched once per game exactly like categories. The category and sort `Select`s and the Tags trigger all carry a leading `lucide` icon (`Select` gained an optional `icon` prop) so the filter row reads as one set.

**localStorage key convention** — Two scopes:

- App-level (same across games): `modrex:<key>` — e.g. `modrex:active-view`, `modrex:active-game`, `modrex:sidebar-collapsed`, `modrex:mod-cache`, `modrex:files-cache`, `modrex:links-cache`
- Game-scoped (per game): `` `modrex:${GAMES[activeGame].storageKey}:<key>` `` — e.g. `modrex:pd3:installed-view`, `modrex:pd3:browse-sort`, `modrex:pd3:collapsed-folders`

`GAME_SPECS` in `src/shared/types.ts` is the renderer's game registry: `GameId = keyof typeof GAME_SPECS` and `GAMES: Record<GameId, GameSpec>` derive from it, so **adding a game is one entry there** — `GameId`, the `isGameId` guard, `WelcomeScreen`'s picker, and `App`'s valid-id check all follow automatically. `GameSpec` fields: `workshopId` drives modworkshop API calls; `storageKey` scopes localStorage keys; `hasNews` gates the News nav view (Nexus availability now comes from the source registry, not a spec field); `requiredLaunchFlag` is the launch argument a game needs for mods to load (PD3's `-fileopenlog`; absent = none), consumed by `TopBar`'s pre-launch warning and `SettingsPage`'s launch-options hint. It must stay in sync with Rust's `GAME_REGISTRY` (`commands/games.rs`) — `pnpm check-games` (CI) diffs the two id lists. Never hardcode `'pd3'` or `853` where `activeGame` is available — use `GAMES[activeGame].*`. `BrowsePage` remounts on game change via `key={activeGame}` in `App.tsx` — browse cache and sort preference are both scoped per game.

**`deps.ts`** — dependency-warning logic shared by `ModDetailPage.tsx` and `BrowsePage.tsx` (the loader half of the surrounding state now lives in `hooks/useLoaderState.ts` below; the deps-warning modal state is still per-component by design). `collectDeps`/`isOffsiteDep`/`isLoaderDep`/`missingRequiredDeps`/`offsiteDepHost` are generic and game-agnostic. `collectDeps` sorts by the author-defined `order` field (id as tiebreak, matching modworkshop's mod-tabs sort) — the result's sequence is the author's intended install order, and `DepsTab` numbers rows from it, so never re-sort or re-group downstream. **Two different ways a "loader" dependency is represented**: SuperBLT is hosted _externally_ (no modworkshop mod page), so it's an offsite dependency detected by a `blt` substring heuristic (`isLoaderDep`) and checked via `loaderInstalled: boolean | null` — **PD2 only**, since the check looks for `WSOCK32.dll`/`IPHLPAPI.dll`/`libsuperblt_loader.so` and PDTH's loaders are `DINPUT8.dll` and `lightfx.dll`; every other game leaves that state null. Every other loader is _hosted_ on modworkshop, so it's checked via the `loaderModIds: Record<number, boolean | null>` param — `missingRequiredDeps` looks the dependency's `mod.id` up there before falling back to the normal installed-list check.

**`ModSummary` vs `Mod` (`src/shared/types.ts`)** — a list entry and a full mod are now different types, and the distinction is enforced. `ModSummary` is what `listMods`, `nexusSearchMods`, `syntheticMod` and the installed-metadata refresh produce; `Mod` extends it with the fields only `/mods/{id}` returns (`images`, `banner`, `dependencies`, `instructs_template`, `tags`, `members`, changelog/license/repo_url). Because the collections are **required but possibly empty**, a `ModSummary` is NOT assignable to a `Mod` — turning that on caught roughly 20 places that were declaring `Mod` while holding list data (`BrowsePage`'s `result`, five `modData` maps, `ModCard`/`ModListRow`/`FileSelectModal` props, `browseCache`). Both types must stay structurally identical to the generated ones in `bindings.ts`: `api.ts` assigns the command result **without a cast**, so drift is a compile error there. That is why nullable fields are written `| null` and not `?:` — Rust `Option` exports that way, and loosening them back breaks the check rather than fixing anything.

**`sources.ts`** — the renderer half of the source registry, mirroring Rust's `SOURCE_REGISTRY` (`commands/sources.rs`), which owns which sources exist, the games each serves, and the id each knows a game by. `loadSourceRegistry()` runs once at startup (`App.tsx`) so lookups stay synchronous inside render paths. `sourcesForGame(gameId)`, `hasSource(gameId, sourceId)` and `nativeIdFor(gameId, sourceId)` replaced the scattered `GAMES[activeGame].nexusDomain !== undefined` checks; **`nexusDomain` no longer exists on `GAME_SPECS`**. RAID has no Nexus entry, so `sourcesForGame` returns one source for that game only.

**`components/SourceSelect.tsx`** — the Browse source switcher, rendered by both browse pages. **Results are deliberately NOT merged across sources** (owner decision): the two have separate search engines, so sort options differ, relevance scores are not comparable, and page cursors are independent. One source is active at a time and each page keeps its own query, sort and page. Renders nothing when a game has one source. Its per-source mod counts come from a **module-level shared store, not component state**: both browse pages stay mounted and each renders a switcher, so with local state whichever instance's fetch was cancelled kept an empty map forever and one tab showed counts while the other did not. Subscribers are notified on every write and an `inFlight` map stops the two instances issuing the same request twice. Counts are library-wide (unfiltered) and fetched once per session, behind `waitForForegroundClear()` so they yield to the actual browse results; Nexus checks `isNexusSignedIn()` first rather than firing a request that would fail, and shows no count when signed out.

**`loaders.ts`** — the renderer half of the loader registry, mirroring Rust's `LOADER_REGISTRY` (`commands/loaders.rs`), which owns which loaders exist, the modworkshop ids each is published under, and the games each serves. `loadLoaderRegistry()` runs once at startup (`App.tsx`) so the lookups can be synchronous inside render paths. `loadersForGame(gameId)`, `loaderForModId(gameId, modId)` (a dependency id → its loader), `buildLoaderModIds(gameId, state)` (expands per-loader state across every id it's published under — UE4SS has three), and `resolveLoaderState(...)` (presence-checks only the loaders a mod actually depends on) replace the old hardcoded id tables. `LoaderState` is `Record<loaderId, boolean | null>`; `null` means unchecked, and loader deps are only reported missing on a definitive `false`. Install dispatch reads `viaModFlow`: false → `api.installLoader(id, gamePath)`, true (UE4SS) → the normal `api.installMod` flow. **Adding a game's loader is one Rust registry entry with no renderer edit.**

**`hooks/useLoaderState.ts`** — the shared loader state behind `BrowsePage` and `ModDetailPage`, which previously kept near-identical copies (both of the bugs fixed in `fix(deps): surface install prompts on dependency rows` lived in that duplication). Returns `loaderState`, `setLoaderFlag`, `refreshLoader(id)`, `installLoader(loaderModId)`, and `loaderModIds`. `installLoader` is the single registry-driven dispatch — `viaModFlow` loaders (UE4SS) ride `api.installMod`, everything else calls `api.installLoader` — and **returns the post-install presence rather than assuming success**: a loader can be on disk and still unusable (SuperBLT on PD2's Diesel 3.0 branch), and an optimistic `true` made the UI claim Installed while the install flow reported it missing. The presence-check effects deliberately stay in the components: `BrowsePage` checks every loader with a mod page on activation, `ModDetailPage` only the loaders the open mod depends on. The deps-warning modal state stays per-component too (`BrowsePage` tracks which mod triggered it; `ModDetailPage` is inherently per-page). `NexusBrowsePage` has no deps-check logic at all — Nexus mods carry no modworkshop dependencies.

**`formatCheck.ts`** — `SUPPORTED_FORMATS = new Set(['pak', 'zip', '7z', 'rar'])` is the single source of truth for installable formats. `.tar.gz` and `.tar.xz` are handled as a special double-extension case in the URL fallback path. `isUnsupportedFormat(type, downloadUrl?)` returns `true` when a file should show a warning before installing: checks `type` first; if undefined, infers from the URL path's file extension. Every install entry point (`BrowsePage.handleInstall`, `ModDetailPage.handleInstall`, `DownloadsTab.handleInstallFile`, `FileSelectModal.handleInstallSelected`) must call this before proceeding. When adding support for a new file format, add it to `SUPPORTED_FORMATS` here.

**`hooks/useModData.ts`** — fetches remote mod metadata for all installed mods. **Two parallel per-source branches**: the modworkshop branch (below) does one batched `ids[]` fetch; the Nexus branch fetches one mod at a time via `getCachedNexusMod`/`nexusModCache.ts` (no batch metadata endpoint exists, and Nexus's hourly quota is undocumented) — both write into the same `modData: Map<number, Mod>` keyed by each mod's **local** `id`, translating to/from the real `remoteId` at the API boundary in each branch independently. Signature is `useModData(installed, workshopId)` — `workshopId` is needed because the bulk refresh goes through `/games/{id}/mods`; `InstalledPage` passes `GAMES[activeGame].workshopId`. On each `installed` change, it bails early (via a sorted-id string stored in a `useRef`) when the set of installed mod IDs is unchanged — this avoids redundant re-runs on focus-refresh cycles that produce new array references. Otherwise, it first synchronously pre-populates `modData` from `getInstalledMetaEntry` (instant, no API call) and marks fresh entries in `fetchedAt` so they skip the network fetch — freshness window is `INSTALLED_META_TTL_MS` (30 min, imported from `modCache.ts` so the two stay in lockstep). Then it makes one call to `fetchInstalledModsMeta(workshopId, staleIds)` — a single batched fetch via the `ids[]` listing filter instead of fanning out one request per mod (see `modCache.ts`). Per-mod freshness is still tracked in the same `fetchedAt` `useRef` so re-renders don't re-trigger fetches. **When `installed` becomes empty (game switch), `modData`, `failedIds`, and `fetchedAt` are all reset immediately** — this prevents stale metadata from the previous game from bleeding through on the next game's render. Mods with no catalog link (`!hasCatalogLink(m)`, `installedUtils.ts`) are never fetched and never added to `failedIds` — a locally identified mod with no catalog entry has nothing to fetch. Returns `modData: Map<number, Mod>`, `failedIds: Set<number>`, and `updatable: InstalledMod[]`. `updatable` deduplicates by `id` and skips any mod where the latest remote version is already installed (handles multi-file mods that share an `id`). Mods whose installed `version` is missing or `"unknown"` are never flagged updatable — an unidentified or embedded-id mod with no comparable version must not nag a perpetual false update. **`"outdated"` is a deliberate exception**: both `identify_untracked`'s `by_name()` fallback and `upgrade_negative_ids` set it (instead of `"unknown"`) specifically when a name match succeeds _after_ a SHA256 check against the index's current file already failed — that's a confirmed signal the installed bytes are stale (the mod's modworkshop file was updated since install), not just an absence of information, so it's allowed to surface as updatable rather than being suppressed.

**`hooks/installedUtils.ts`** — pure data helpers. **Three separate questions, three helpers, and mixing them up is the bug this split exists to prevent**: `isIdentified(m)` asks _what is this mod_ and reads `m.identity` at Exact or Strong confidence, so a mod published only on its author's own updater (`pd2mods.z77.fr:Celer`) is identified exactly as much as a ModWorkshop one, and a Candidate guess never counts; `hasCatalogLink(m)` (`!!m.remoteId`) asks _can we fetch it from a catalog_ and is what browsing, thumbnails, update checks, reinstall, the mod detail page and the Nexus-identify affordance all actually need; `identityKey(m)` is the grouping key, project identity first (namespace and key together, never the key alone) and the installed record only as a fallback; `withDeclaredMetadata(m)` swaps in the name, author and version a mod's own files declare when no catalog describes it, applied once at the top of `InstalledPage` so search, grouping and every row agree. When the split landed, every component call site turned out to want `hasCatalogLink` — only grouping and the Health Check's unidentified bucket wanted identity — so reach for `hasCatalogLink` unless you specifically mean "do we know what this is". `InstalledMod.id` remains the installed record's own key (React keys, DnD, command targets), never the project identity (see the `InstalledMod.id` domain fact in the root `CLAUDE.md`). `syntheticMod(ins)` constructs a fallback `Mod` object for unidentified and fetch-failed mods — the pattern is `apiMod ?? syntheticMod(ins)` after the skeleton guard, so unidentified mods render with their local name instead of a skeleton. `modworkshopRemoteIds(mods)` extracts real, deduplicated modworkshop ids for the handful of call sites that need to fetch fresh data by real id (e.g. dependency checks) — never pass a local `id` to a real API call. `getAllModsInFolder(mods, folders, folderId)` recursively collects all mods in a folder subtree (direct children plus nested folders); used for bulk enable/disable on folder toggle. `normalizeModScopes(mods)` — for rendering only, collapses multi-folder entries for the same identified mod only when some of those entries are at root (the split-install artifact where reinstalling puts some paks at root). Intentional multi-folder layouts (all entries in non-root folders) are left untouched. `foldersEmptiedByNormalize(raw, normalized, folders)` computes the folders whose entire subtree was pulled to root by that collapse — `computeChildren`'s optional `hiddenFolderIds` param (threaded from `InstalledPage` through `InstalledContext` to `FolderSection`) hides them, so a folder holding only a collapsed multi-pak mod (e.g. a skin archive in a folder plus its required bare pak at root) doesn't render as an empty duplicate next to the mod's root card; folders that were already empty before normalization (fresh drop targets) stay visible. Called in `InstalledPage` as `renderMods = normalizeModScopes(displayMods)` before passing to `computeChildren`. `computeChildren(mods, folders, parentId, visibleFolderIds?)` builds and sorts children (mods before folders, both descending by priority) — filters out folders that have no mods in the normalized array (prevents empty auto-created folders from appearing); the optional `visibleFolderIds` set filters folders not matched by search. `groupChildren` collapses consecutive mod runs into `root-group` grid slots; `filterInstalled(mods, folders, query)` returns matching mods and the set of all ancestor folder IDs that must remain visible. `InstalledGroup = { key: string; id: number; mods: InstalledMod[] }` and `groupInstalledByIdentity(mods)` — groups by `identityKey` (`identity:<namespace>:<key>` when the project is known, else `id:N` for a catalog install, else `uid:X`); the canonical grouping used by the health check and the mod counter. `detailNavArgs(ins)` resolves the real remote id (+ `'nexus'` source flag when applicable) needed to navigate to `ModDetailPage`, uniformly for both sources via `remoteId`. `HealthSummary` and `computeHealthSummary(mods)` — purely local health categories (missing, archiveBroken, outdated, unidentified), no network. **`unidentified` means Modrex could not work out what the mod is at all**, not "not on ModWorkshop": a mod with a resolved local identity and no catalog entry is not a health problem and does not appear there. `outdated` needs `hasCatalogLink`, since "something newer exists" is unanswerable without a catalog. `outdated` catches two cases: `version === 'outdated'` (SHA256 mismatch, set by Rust) and stale duplicates from `findSuspectDuplicateGroups` (bare-uid + archive-scheme uid coexisting for the same `fileId`). `healthIssueCount` in `InstalledPage` sums missing + archiveBroken + outdated + unidentified to drive the badge on the health check button — dependencies and updates are intentionally excluded from the badge.

**`hooks/useDragDrop.ts`** — all reorder-DnD state and handlers. Reordering runs on **pointer events, not HTML5 drag**: `dragDropEnabled: true` in `tauri.conf.json` (required for the drop-a-file-to-install flow — Tauri's native `onDragDropEvent`, wrapped as `api.onFileDrop` and consumed by `useFileDropInstall`/`FileDropOverlay`, is the only way to receive dropped file _paths_) disables HTML5 drag events in the webview, so the hook implements dragging itself. `onModPointerDown`/`onFolderPointerDown` arm a pending drag that starts after a 5 px movement threshold (pointer-downs on `button, a, input, textarea, select, [data-no-drag]` never arm); `pointermove` hit-tests `document.elementFromPoint` against the `data-drop-mod`/`data-drop-folder-header`/`data-drop-empty-folder`/`data-drop-child` attributes via pure `compute*DragOver` functions returning a `DropTarget`, auto-scrolling near the edges of the container behind `scrollContainerRef`; `pointerup` applies the target (`applyModReorder`/`applyDropIntoFolder`/`applyChildDrop`/`applyNestFolder`). Escape cancels, and a capture-phase click listener (removed on the next tick) swallows the click the browser fires right after a drop so it can't open the mod detail page. Mods with `location` set (secondary-target, e.g. `mod_overrides`) are blocked from cross-folder drags and into-folder drops — `computeModDragOver`'s cross-folder path, `computeFolderHeaderDragOver`, `computeEmptyFolderDragOver`, and the apply-side guards in `applyModReorder`/`applyDropIntoFolder` all check `srcMod.location`. Same-scope reordering is still permitted.

**InstalledPage component family** — `InstalledPage.tsx` is a ~230-line coordinator; the logic is split across focused files:

- `hooks/useFolderActions.ts` — all folder state (rename, delete, create, collapse, toggle-enable) and their API calls. Owns `renamingFolderId`, `deletingFolderId`, `creatingFolderParentId`, `collapsedFolders`, `loadingFolderId`.
- `hooks/useModActions.ts` — mod operation state: `loadingMod`, `reinstallProgress`, `reinstallError`, `refreshing`, `zipPickerData`. Owns `handleUninstall`, `handleEnable`, `handleDisable`, `handleReinstall`, `handleRefresh`. `handleReinstall` pre-uninstalls all missing entries before calling `installMod` — necessary because ZIP-installed paks use `{file_id}_{stem}` uids but `install_mod` creates `{file_id}`, leaving stale missing entries without this cleanup. `reinstallError` surfaces in `InstalledPage` as a dismissible banner; `clearReinstallError` resets it.
- `components/InstalledContext.tsx` — React context that `InstalledPage` provides and all descendants read via `useInstalledContext()`. Contains mod data, view mode, gamePath, `activeGame: GameId`, folder/mod action handlers, and all DnD handlers. Any new component that needs shared installed-page state should read from this context rather than adding props.
- `components/FolderSection.tsx` — renders a folder row + its contents recursively. Also exports `NewFolderInput` (used at root level in `InstalledPage` and inside folders). Reads everything from `InstalledContext`.
- `components/InstalledModItem.tsx` — renders a single mod group (list or grid variant based on `viewMode` from context). Contains the skeleton guard, `combined` InstalledMod construction, and all per-mod DnD handlers. `combined.enabled` is `mods.some(m => m.enabled)` — the group is shown as enabled if any file is enabled; only all-disabled triggers the disabled state. When `mods.length > 1`, renders a clickable "N files" badge that opens `ManageFilesModal`.
- `components/ManageFilesModal.tsx` — modal for per-file management of multi-pak mods. Uses the `Dialog` primitive (which portals into `document.body`, avoiding drag-behind from the parent draggable div). Groups files by their real `folderId` from raw `installed` (bypasses `normalizeModScopes`). Renders root-level files flat, folder groups as collapsible rows with a chevron + folder name + count + Toggle + delete button. File rows show filename + Toggle + delete. Folder-level and file-level toggle/delete operate independently. **Stale-duplicate detection**: `installedUtils.ts`'s `findSuspectDuplicateGroups` flags the exact orphan shape `install_from_zip_entry`'s pre-removal fix (above) now prevents going forward — a bare-uid entry (`uid === String(fileId)`, the `install_mod`/`install_file` scheme) coexisting with an archive-scheme entry (`uid` prefixed `"{fileId}_"`) for the same `fileId`. This is deliberately narrower than "same id, different version," which produced false positives on real mods that ship several independent files under one listing (verified live against a mod with 7 separate `.pak` files). `resolveStaleDuplicates` confirms which side is actually stale using the mod's live file `type` (pak vs zip/7z/rar) from `getCachedModFiles`, rather than guessing from install timestamps — only `ManageFilesModal` runs this (it already fetches file data), badging the stale file "Outdated" via `installed.manageFiles.staleDuplicateBadge`. `InstalledModItem`'s "N files" badge only runs the cheap structural check (no network) to decide whether to tint itself as a hint.
- `components/UpdatesModal.tsx` — owns `selectedIds`, `loadingMod`, `updatingAll`, `updateError` internally. Renders each row through an extracted `UpdateModalRow` component (not inline in the `.map()`) specifically so it can call `useThumbnail` — hooks can't be called inside `.map()`, and a Nexus mod's `thumbnail.file` is already an absolute CDN URL (`useThumbnail` passes it through untouched), unlike modworkshop's relative filename. Update/install calls resolve the real remote id via `Number(ins.remoteId)` rather than `ins.id`, with an early-return guard on an invalid value.
- `components/HealthCheckModal.tsx` — report modal opened after `runHealthCheck` in `InstalledPage`. Six tabs: dependencies, missing files, broken archives, outdated, unidentified, updates. Bulk action (tab-specific) lives in a fixed footer, never inside the scrollable list. Per-row dep "Install" calls `api.installMod` directly (UE4SS is handled entirely in Rust and never surfaces a picker sentinel). After any dep install, `handleDepInstalled` in `InstalledPage` refreshes the installed list and re-runs `checkMissingDependencies` against the fresh data — two `api.getInstalled` calls are intentional: `onRefreshInstalled` (= `refreshInstalled` in `App.tsx`) updates App state but returns nothing, so a second local fetch (~2ms filesystem) provides the fresh list for the dep re-check. `missingDeps` is a snapshot prop; the re-check via `onDepInstalled` is the only way to update it while the modal is open.
- `components/DeleteFolderModal.tsx` — stateless confirm dialog; `onConfirm`/`onCancel` as props.
- `components/ErrorBoundary.tsx` — class component wrapping the entire app; catches render errors, logs them via `@tauri-apps/plugin-log`, and shows a minimal crash screen.

### Strings (i18n)

All user-visible strings live in `src/renderer/src/i18n/en.json`. Use the typed helper:

```ts
import { t } from '../i18n'
t('common.install')
t('browse.modCount', { total: 42 })
```

`t(key, vars?)` is fully type-safe — TypeScript errors on unknown keys. Top-level namespaces: `common`, `app`, `errorBoundary`, `topBar`, `sidebar`, `browse`, `installed`, `news`, `detail`, `embed`, `fileSelect`, `zipPicker`, `depsWarning`, `settings`.

**Multi-locale**: the `i18n/` folder holds only locale JSON files — the logic that reads them (`i18n.ts`, `locales.ts`) lives one level up alongside the other renderer modules, so the folder stays a plain set of translation files. There is no manual locale registry: `locales.ts` discovers every `i18n/*.json` file at build time via `import.meta.glob` (`LOCALE_IDS`, `isLocaleId`), and its picker label comes from `Intl.DisplayNames` (a language's own name for itself) rather than a hand-maintained string — so a new locale is one JSON file, nothing to register. `en.json` is the canonical key set — every other locale is typed as a `DeepPartial` of it (the cast happens once, at `BUNDLES` in `i18n.ts`, since a glob-discovered file's shape can't be checked by TypeScript), so a translation missing a key still compiles; `t()` falls back to the English bundle, then the raw key, for anything unresolved. `useLocale()` (`useSyncExternalStore` over a module-level store backed by `localStorage['modrex:locale']`) drives `App.tsx`'s `key={locale}` on the root element, so a language switch remounts the whole tree rather than relying on ordinary re-renders — `BrowsePage` is wrapped in `memo` specifically to skip re-renders, so a plain state change would never reach it. Everything in `App`'s own state and refs (`installed`, `gamePath`, `settingsCache`, etc.) lives above the returned JSX and survives the remount, so switching language never re-detects the game path or re-fetches the installed list. **Never call `t()` at module scope** (a top-level object/array literal) — it freezes at import time and never reacts to a switch; an ESLint rule in `eslint.config.js` blocks this. Call it inside the component instead, normally via `useMemo`. `pnpm check-i18n` (pre-commit + CI) diffs every locale file's keys and `{var}` tokens against `en.json` — see `CONTRIBUTING.md` for the contributor-facing "adding a language" steps.

**Page header height** — `components/pageHeader.ts` exports `TITLE_ROW_H` and `TITLE_ROW_MIN_H`, and **they must stay the same number**. Browse's source switcher is the tallest thing that sits on a title row; its height used to be derived from its own contents, which made it depend on font metrics AND on whether a mod count had loaded (a skeleton is not the height of the text it replaces). Both made Browse's header a few pixels taller or shorter than the other pages, so the search bar under it drifted when moving between Browse, Installed, News and the game picker. `TITLE_ROW_H` fixes the switcher's height; every other page's title row reserves `TITLE_ROW_MIN_H`. Any new page with a title row should use it.

Skeleton loading: `components/SkeletonCard.tsx` (grid) and `components/SkeletonListRow.tsx` (list). `ModCard` accepts `installedCount?: number` — when > 1, shows a "N files" badge over the thumbnail (same style as `InstalledPage`); `BrowsePage` builds `installedByModId: Map<number, InstalledMod[]>` via `useMemo` and passes `installedByModId.get(mod.id)?.length || undefined` for O(1) lookup per card. `ModCard` also accepts `onPrefetch?: () => void` called on `onMouseEnter` — `BrowsePage` wires this with a 150 ms debounce that fire-and-forgets `getCachedMod`, `getCachedModFiles`, `getCachedModLinks` so the detail page loads from cache on click.

**Skeleton guard**: render a skeleton only when `!apiMod && !failedIds.has(id) && isModworkshopSourced && hasCatalogLink(ins)` (`InstalledModItem.tsx`) — both conditions are load-bearing. `hasCatalogLink` (not `id`'s sign — `id` is opaque for every source, see the root `CLAUDE.md`'s `InstalledMod.id` fact) gates unidentified mods, which are never fetched and never added to `failedIds`, so without it they'd render as permanent skeletons. The modworkshop-source check is separate and just as necessary: Nexus's own fetch trickles in slowly (rate-limited, one at a time via `useModData`'s Nexus branch), so a Nexus mod always falls straight to `syntheticMod` instead of blocking on a skeleton — mirroring the same source split in `InstalledModItem`'s `handleOpen`.

**Confirm dialogs**: never use `window.confirm`. All modals use `components/Dialog.tsx` — a thin wrapper around `@radix-ui/react-dialog` that provides focus trap, scroll lock, Escape key, and portal rendering. Pass `open`, `onOpenChange`, `title` (screen-reader only), and a `className` with width/height constraints. The `Dialog` component carries `text-text` on its Content so portaled children inherit the correct text color — any new portaled component must do the same. Do not use `fixed inset-0 z-50` manual overlays or `createPortal` for modals.

**ModDetailPage loading model**: three distinct loading states. (1) `loading` — full-page spinner, true only when no mod data at all (cold cache, no `initialMod`). Sync-initialized from `getModCacheEntry(modId)` and the `initialMod` prop — starts `false` when either is available. (2) `filesLoading` — Downloads-tab-only spinner, true until files + links resolve. Sync-initialized from `getFilesCacheEntry(modId)` — starts `false` when the files cache is warm. (3) `error` — hides the entire page; only set on mod-data-load failure, never on files/links failure. `fetchData` fires two independent parallel chains: `getCachedMod` sets `loading = false` when resolved; `Promise.all([getCachedModFiles, getCachedModLinks])` sets `filesLoading = false` when resolved. This means the header and description render as soon as mod data is available, without waiting for files/links. `initialMod?: ModSummary` accepts the browse-list summary — enough for the header. The loaded detail is tracked SEPARATELY as `detail`, with `mod = detail ?? initialMod` serving the header, so detail-only fields must read from `detail`. That split is what stops a half-loaded page claiming it has images or tags; it also replaced a runtime `mod.dependencies === undefined` check that was doing the same job by hand. `installError` is a separate dismissible banner that coexists with the page content — never conflate it with `error`.

**ModDetailPage error states**: `error` (set by `fetchData` mod chain) hides the entire page content — only set it on mod-data-load failures. `installError` is the install-operation error — a dismissible banner that coexists with the page content. Install handlers (`handleInstall`, the `NonPakConfirmModal.onConfirm` callback) must be `async` and `await doInstall()` inside a `try/catch` that calls `setInstallError`; omitting the `await` turns errors into silent unhandled rejections. `doInstall` clears `installError` at entry so it resets automatically on each new attempt.

**`modDetail/DownloadsTab.tsx`**: branches on an `isNexus` prop throughout rather than being two components — a modworkshop file row installs directly; a Nexus file row instead opens `nexusUrl` with `nmm=1` (Nexus's own mod-manager-download deep link param, verified against Vortex's source) to auto-trigger that file's "Mod Manager Download" button, then shows an "awaiting" state (`awaitingNxmFileId`) until the resulting `nxm://` link lands and installs — there is no synchronous download response to await. Nexus files are grouped by Nexus's own category convention (`groupNexusFiles`/`NEXUS_CATEGORY_ORDER`: MAIN/UPDATE/OPTIONAL/OLD_VERSION/MISCELLANEOUS, matching the site's own file-list layout) instead of modworkshop's flat list. Per-file images, external links, and the offsite-download fallback are all modworkshop-only (`!isNexus` gated) — Nexus has no per-file images, only the one mod-level picture already shown elsewhere on the page.

**DepsWarningModal on the detail page**: `onGotIt` only dismisses the modal and records the dismissal — it does not re-call `doInstall`. The user must click Install again. This is intentional.

**Archive install flow**: `ZipPickerModal` handles multi-pak archives (ZIP, 7z, tar.gz, tar.xz, RAR) — entries default to your previously-installed variant(s) when this is an update (matched by filename against the existing install, since the new file's id never matches the old one) or to every entry on a fresh install; installs sequentially, calls `api.deleteTempFile(zipPath)` after all entries finish. The picker's two pieces of reusable logic — `computeAutoUpdateSelection` (the filename-matching above) and `installZipPickerEntries` (the actual install loop, factored out so it can run without ever showing the modal) — are both exported from `ZipPickerModal.tsx`. `UpdatesModal` calls them directly on a `needsPicker` outcome: if every previously-installed file variant has a filename match in the new archive, it silently reinstalls just those files and never shows the picker at all — only a genuinely ambiguous case (no prior install, or no filename match) falls back to opening it. `UpdatesModal`'s "Update Selected" batch runs through a `queueRef`-backed `processQueue` loop: hitting a prompt outcome that does need a picker (this one or any of the three siblings below) pops that mod off the queue, opens the modal, and pauses; the modal's `onClose` calls `processQueue` again to resume with the next queued mod, so a multi-mod batch update completes on one click even when one mod along the way needs a manual decision. When the archive is "structured" (entries span more than one directory after stripping a common wrapper prefix), `ZipPickerModal` renders folder groups and automatically creates app folders per subdirectory before installing — `getRequiredDirs` returns all needed paths shallowest-first so parents are created before children; `stripWrapperPrefix` keeps flat-only wrappers intact (their name becomes an app folder) and only strips the prefix when entries mix root-level paks and subdirectories. Folder auto-creation is skipped when `payload.targetTag` is set — secondary-target mods can't be placed in primary-target app folders. **Also skipped for Crime Boss pak entries** (`gameId === 'cb' && payload.entryKind !== 'dir'`, via `isCrimeBossPakArchive`): `install_from_zip_entry` always re-synthesizes its own `Content/Paks/WindowsNoEditor` skeleton for CB pak entries via `extract_entry_into_crimeboss_skeleton` regardless of the entry's original path inside the zip (see the Crime Boss domain facts below), so a CB pak archive whose entries all share one ModKit-wrapped directory (a common shape — multiple pak variants packaged together by the official ModKit) is never treated as "structured"; otherwise the modal would recreate that wrapper as real app folders and the backend would nest its own skeleton inside them, doubling `Content/Paks/WindowsNoEditor`. CB directory entries (`entryKind === 'dir'`, UE4SS sub-mods or host-pack candidates) are unaffected and still get normal structured handling. The Rust command `install_from_zip_entry` (name kept for backwards compat) uses `extract_entry` internally and dispatches by magic bytes, so it handles all supported archive formats. The install commands resolve with a typed `InstallOutcome`; a multi-pak archive arrives as the `needsPicker` variant carrying `ZipMultiPakPayload` (the name covers all supported archive formats, not just ZIP). `ZipMultiPakPayload` carries `targetTag?: string` plus an optional parallel `entryTags?: (string|null)[]`; when `entryTags` spans more than one target (a mixed mods+overrides modpack) `ZipPickerModal` groups entries by destination and installs each with its own `locationTag` and no app-folder creation. Three sibling prompt outcomes render their own modals: `needsHostChoice`/`HostPackModal` (install a content pack into its host mod via `installHostPack`, or offer to install the host first when absent), `unrecognized`/`UnrecognizedArchiveModal` (show the mod's instructions instead of mislaying the files), and `needsCbFlatConfirm`/`CrimeBossFlatArchiveModal` (confirms installing a Crime Boss archive with no enclosing folder, since every entry sits at the zip root and there's only one possible destination). All four are wired into `BrowsePage`, `ModDetailPage`, its `DownloadsTab`, the Installed-page reinstall flow (`useModActions.handleReinstall` → modals rendered by `InstalledPage`), and the Updates modal (`UpdatesModal`). `FileSelectModal` handles ZIP\*MULTI_PAK inline: it pauses its install loop (via a Promise resolved by `zipResolveRef`), renders `ZipPickerModal` after its own main div (so it appears on top at the same `z-50`), then resumes with the next file when ZipPickerModal closes. When adding a new install entry point that calls a Rust install command, handle the resolved `InstallOutcome` in full, normally via `handleInstallOutcome` (`installSentinels.ts`), whose required handlers object makes a missed prompt a compile error (back when these rode the error channel as sentinel strings, the reinstall path and later the Updates modal each shipped missing one).`InstalledMod.archiveBroken`(previously`zipArchive`) is set by `mark_archive_files`when an installed pak file is detected as an archive by magic bytes; persisted in the state file and cached across launches — shown as a warning badge in`ModCard`and`ModListRow`.
