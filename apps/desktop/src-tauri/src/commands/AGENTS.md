# Backend commands (`src-tauri/src/commands/`)

Paths are relative to `apps/desktop`.

- **`settings.rs`** — reads/writes `settings.json` in Tauri's `app_data_dir()` (`%APPDATA%\Modrex\` on Windows, `~/.config/modrex/` on Linux). Top-level fields: `skipFileOpenLogWarning`/`dismissedDepsWarnings` (global flag + list, PD3-only warning — see TopBar), `games: Option<HashMap<String, GameSettings>>`. `GameSettings` holds `game_path?`/`launcher?` (genuinely optional — not-yet-detected) plus `install_pinned` (see `src-tauri/src/commands/launchers/AGENTS.md`: the two path fields name one store's copy together, and there is deliberately **no command that writes `launcher` on its own** — the removed `set_launcher` was exactly that, and it let Modrex mod one copy while launching another) plus `launch_options`/`suppress_crash_reporter`/`crimeboss_install_mode` per game. The latter three, and every `Settings` field with a well-defined default (`skip_file_open_log_warning`, `dismissed_deps_warnings`, `analytics_consent_asked`, `analytics_enabled`, `discord_rich_presence_enabled`, `successful_installs`, `first_install_at`, `support_prompt_shown`), are plain non-`Option` types with `#[serde(default[ = "fn"])]` rather than `Option<T>` — `null` never appears in settings.json for a field that only ever means "use the default"; `Option` is reserved for fields with a real third state (not-yet-detected paths/launcher, `analytics_id`, `nexus_oauth`, or the legacy flat fields below). Both `GameSettings` and `Settings` have hand-written `impl Default` (not derived) because two fields default to a non-zero value (`discord_rich_presence_enabled: true`, `crimeboss_install_mode: "auto"`) that `#[derive(Default)]` wouldn't produce. Legacy flat fields (`game_path`, `launcher`, `launch_options`) carry `#[serde(skip_serializing, default)]` so old settings files still deserialize but writes always use the new `games` map. `migrate_settings(s: Settings) -> Settings` promotes legacy flat fields to `games["pd3"]` on first read — called inside `read_settings`. `game_settings<'a>(s, game_id) -> Option<&'a GameSettings>` is the canonical helper for reading per-game config; always use it instead of touching legacy fields directly. Commands: `get_game_settings(game_id: String) -> GameSettings` (new); `set_launch_options`, `configure_game_path`, `detected_installs`, `set_suppress_crash_reporter` all accept `Option<String> game_id` defaulting to `"pd3"` for backwards compatibility. On first launch after an upgrade from the old Tauri identifier, `migrate_from_old_identifier` copies `settings.json` and `mod-index.db` from `%APPDATA%\io.github.shulhaoleh.pd3modmanager\` on Windows, `~/.config/io.github.shulhaoleh.pd3modmanager/` on Linux. Called from `lib.rs` setup hook before the window shows. `reset_app_settings` factory-resets settings.json to `Settings::default()` through `update_settings` (clearing every game path, launcher choice, analytics consent + id, and preference); it never touches installed mods, game files, or the on-disk caches. The renderer pairs it with wiping all `modrex:` localStorage keys and reloading, for a genuine first-run reset.

- **`api.rs`** — modworkshop REST API via one pooled `reqwest` client. `get_mod` is the authoritative detail contract and carries computed `version` plus the current default `download`; `list_mods` is browse/display metadata and deliberately carries neither. `get_mod_versions` calls `/mods/versions`, deduplicates IDs, chunks at the verified 100-ID maximum, and returns explicit known/unversioned/missing/failed states matched by ID. `list_mods` accepts repeated `ids[]` for bulk display metadata and `tags[]`/`block_tags[]` for Browse filters. modworkshop enforces **90 req/min per IP, shared across every endpoint**. Requests share a token bucket (burst 4, 1.3 req/s sustained), remaining-budget slowdown, a three-request semaphore, and one pooled client. Transport failures and 408/429/5xx responses retry up to three sends with bounded `Retry-After` or jittered exponential backoff; permanent 4xx responses fail immediately. **HTTP_CLIENT invariant**: every outgoing HTTP request anywhere in the Rust backend must go through `http_client()` from `api.rs` — never call `reqwest::Client::new()` directly. Both `http_client()` and `user_agent(app)` are `pub(crate)`.

- **`domain.rs`** — the neutral mod shapes every source translates into, plus the ModWorkshop and Nexus translations. **Listing and detail are separate contracts**: `ModSummary` contains only fields guaranteed by `/games/{game}/mods`; `ModDetail` additionally requires computed `version`, default `download`, and the richer detail collections from `/mods/{id}`. Missing summary version/download must never be normalized to empty placeholders because absence is semantically different from an explicit empty version. Private `Wire*` types absorb provider nullability while public IPC types remain explicit. `ModDependency.target` is a summary, so dependency version labels are enriched separately instead of pretending an embedded summary is a detail. Nexus update versions continue through Nexus detail metadata and never through the ModWorkshop batch state.

- **`sources.rs`** — resolves the id a mod source knows a game by. `SOURCE_IDS` lists the sources the host implements a connector for; a game reaches one only by declaring a binding in its own `package.toml`, so there is no second list of games here to drift. `native_id` is a string because the two kinds are not alike: ModWorkshop uses a numeric game id, Nexus a domain slug. `nexus_numeric_id` and `game_id_for_native` read the same declarations rather than restating the mapping. `list_sources` hands the result to the renderer (`src/renderer/src/sources.ts`), which is how the Browse source switcher knows a game has more than one source. `source_native_local_id(source_id, remote_id) -> i64` is what `InstalledMod.id` is derived from once a mod is identified, for every source including ModWorkshop — an FNV-1a hash of `"{source}:{remote_id}"`, forced negative (`((hash >> 1) as i64).max(1)` negated). No source is privileged with a raw real id: the earlier scheme (ModWorkshop's real positive id, everything else `-remote_id`) let two different non-ModWorkshop sources collide on the same numeric id, and separately made ModWorkshop an implicit default source in code that had to special-case it. `id` is opaque and never sign-meaningful for any source now; the real id always lives in `InstalledMod.remote_id: Option<String>` — see the `InstalledMod.id` fact in `apps/desktop/AGENTS.md`.

- **`download.rs`** — streams file to `temp_dir()/modrex-{uuid}.{ext}`, emitting `download:progress` Tauri events with `{ downloaded, total }`. `total` is `0` when the server omits `content-length` — callers must handle the indeterminate case.

- **Main-thread invariant**: sync Tauri commands run on the main thread, so a blocked probe freezes the window ("Modrex is not responding"). `auto_detect_game`, `detected_installs`, `configure_game_path`, `select_game_install`, and `is_game_running` are therefore `async` and run their work via `tauri::async_runtime::spawn_blocking` — never convert them back to sync, and route any new detection command through the same pattern. Detection subprocesses (`reg query`, `Get-AppxPackage`) go through `run_bounded` (in `mod.rs`), which polls with a deadline and kills the child instead of `.output()`'s unbounded wait — the same lesson as the old tasklist/WMI freeze fix, now applied to every probe. `run_bounded` sets `CREATE_NO_WINDOW` and pipes stdout itself; it reads stdout only after exit, so it's only suitable for small-output commands (single-line results). Both `detect_game` and `detected_installs` gate each store on `is_installed()` before probing and log `probing <launcher> for <game>` before each `find_game` — the last such line in `Modrex.log` pinpoints a hung probe, which is otherwise traceless. `detect_game` stops at the first hit (one path is all settings can hold); `detected_installs` collects every store's copy, because a game owned twice has two real installations and the launcher picker switches between them.

- **Windows `CREATE_NO_WINDOW` invariant**: The release binary sets `windows_subsystem = "windows"` (`main.rs:1`), so it has no console. Any `std::process::Command` on Windows without `creation_flags(0x08000000)` spawns a visible console window. In debug builds (`pnpm dev`) this is invisible because the process inherits the parent console. Every spawn of a **console-mode executable** (cmd, tasklist, PowerShell, cargo, pkill, pgrep) must use `use std::os::windows::process::CommandExt` and `.creation_flags(0x08000000)`. GUI shell programs (`explorer.exe`, `xdg-open`) are exempt — they never attach to a console regardless.

- **`loaders.rs`** — the mod-loader registry: `LoaderSpec { id, modworkshop_ids, games, detect, install }` and `LOADER_REGISTRY`. A loader is a hook installed next to the game, never tracked in `state.json` and never uninstallable through Modrex, so the five differ only in detection and layout — both captured as data. `DetectStrategy::RootFiles(&[...])` covers SuperBLT (`WSOCK32.dll` current / `IPHLPAPI.dll` legacy / `libsuperblt_loader.so` Linux native, PD2 only), PDTHModOverrides (`DINPUT8.dll` is the proxy and the sole signal; `PDTHModOverrides.dll` is the payload and is installed but not detected), DAHM (`lightfx.dll`), and RAID-SuperBLT (`WSOCK32.dll`/`IPHLPAPI.dll`, no `.so` — RAID has no native Linux build; `IPHLPAPI.dll` may also be the discontinued RaidBLT). `DetectStrategy::Ue4ssProxy` delegates to `ue4ss.rs`, whose proxy DLL and destination vary per `(game_id, launcher)`. `InstallStrategy` is `ExtractEntries` (SuperBLT pulls only `WSOCK32.dll` — the BLT basemod is fetched by the loader itself on next launch; PDTHModOverrides pulls both DLLs), `ExtractAllFlat` (DAHM and RAID-SuperBLT ship framework modules / the Lua basemod inside, so the whole archive lands in the game root), or `ViaModFlow` (UE4SS has no canonical host — each release is a modworkshop mod page, so installs route through the normal mod flow via `zip.rs`'s `UE4SS_LOADER` sentinel). Commands: `list_loaders` (hands the registry to the renderer, which maps dependency ids to loaders instead of restating the tables), `check_loader`, `install_loader` — an unknown loader id is a hard error. `modworkshop_ids` is empty only for SuperBLT, which has no mod page and is matched by the renderer's `blt` name heuristic instead.

**UE4SS** (Lua scripting/native modding framework, supported on both Crime Boss and PD3) splits into two layers that are handled completely differently, and conflating them is the easiest way to get this wrong:

1. **The loader itself** (`commands/ue4ss.rs`) — modeled like SuperBLT/DAHM (presence-detected, one-shot install, never tracked in state), but parameterized per `(game_id, launcher)` instead of hardcoded to one game, because detection genuinely varies: Crime Boss has one maintained release (proxy `dwmapi.dll`); PD3 has **two independently-maintained mod pages** distributing it over time with **different proxy DLLs** (`xinput1_3.dll` for the newer one, `dxgi.dll` for the older one still in real use — e.g. DebugMenuMod, a live PD3 mod, depends on the older page specifically) — both verified against their real downloaded archives, and detection checks every known name per game so it doesn't matter which release a user has. There is no canonical download URL the way SuperBLT/DAHM have (each release is just somebody's modworkshop mod page, no guaranteed long-term host), so install goes through the _normal_ mod-install flow rather than a dedicated fetch — see `zip.rs`'s `UE4SS_LOADER` sentinel in `src-tauri/src/commands/mods/AGENTS.md`.
2. **UE4SS sub-mods** (Lua mods other authors publish separately, dropped into the loader's `Mods/` folder) — these _are_ tracked, via the `ue4ss_mods` `ScanTarget` (Directory-unit, marker `Scripts/main.lua`, added to both `PD3_ENGINE` and `CRIMEBOSS_ENGINE`) and a `mods.txt`-file sync (`mods/ue4ss_modstxt.rs`) instead of file-move for enable/disable.

**The hard part is telling the loader, its own bundled framework sub-mods, and a real third-party sub-mod apart — all three can look identical.** Verified against both real downloaded releases: the full loader zip contains a top-level `UE4SS-settings.ini` _and_ ships ~9-10 bundled framework sub-mods (`ActorDumperMod`, `BPModLoaderMod`, `ConsoleCommandsMod`, etc.) inside its own `Mods/` folder, each with the exact same `Scripts/main.lua` shape a genuine standalone sub-mod has. So: `has_ue4ss_loader_signature`'s top-level-`UE4SS-settings.ini` check is what distinguishes "this download is the whole loader" from "this download is one sub-mod" (a sub-mod never carries that file); and `ModUnit::Directory`'s `excluded_names` list (the verified bundled-module names) is what stops those 9-10 internal modules from being ambient-scanned into Modrex's Installed list as if a user had downloaded them — `index_gated_markers` (the mechanism that solves the equivalent DAHM problem) can't apply here, because `modrex-index` only ever hashes `.pak` files and these are plain `.lua` scripts it never sees. `reconcile_state`'s framework-only purge checks `excluded_names` too, so entries that got ambient-scanned into `state.json` _before_ `excluded_names` existed self-heal on the next load rather than needing a manual fix.

- **`superblt.rs`** — only `is_pd2_diesel3` remains: the Diesel 3.0 branch ships no SuperBLT build, so a present loader still counts as unusable there. SuperBLT's own detect/install data lives in `loaders.rs`.
- **`updater.rs`** — auto-update flow via `tauri-plugin-updater`. `UpdaterState` (managed Tauri state) holds the pending `Update` object and its downloaded bytes across two separate commands. Three-phase sequence: `check_for_update` fetches metadata and stores the `Update` object, emitting `updater:update-available`; `download_update` streams bytes and emits `updater:update-progress` (percent) then `updater:update-ready`; `install_update` takes both and applies. Strategy is always `"manual"` — there is no auto-install path.

- **`thumbnails.rs`** — Thumbnail disk cache. `get_thumbnail(filename)` checks `app_cache_dir()/thumbnails/thumbnail_{filename}`, downloads from `https://storage.modworkshop.net/mods/images` if absent (6-slot semaphore, atomic write via `.tmp` rename), and returns the **cache filename** (not a path) for the renderer to build its `thumb://` URL. By default it downloads the pre-generated `thumbnail_{file}` CDN variant, falling back to the original for old images with `has_thumb: false`; with `full: true` it caches the original under `{filename}`. **Variant policy**: the small variant is only **256 px wide** and upscales badly — use it solely for renders ≤ ~120 px (`ModListRow`'s `w-28` thumb, `DependencyRow`'s 40 px icon); everything wider (`ModCard`, gallery tiles, banner, lightbox) must use `full: true`. The CDN sends no cache headers, so direct CDN URLs cost a download or revalidation round-trip per view — always go through this cache. `cleanup_thumbnail_cache` runs fire-and-forget at startup and removes files whose `modified()` time exceeds 90 days. The modworkshop CDN sends no `Cache-Control` header (`cf-cache-status: DYNAMIC`), so without this every app launch revalidates images over the network. `handle_thumb_protocol` backs the custom `thumb://` URI scheme (registered in `lib.rs`): it serves files from the thumbnails cache dir with `Cache-Control: public, max-age=31536000, immutable`. `sanitize_thumb_filename` percent-decodes the URI path and rejects separators/`..` — every request must pass it before touching the filesystem (path-traversal guard; unit-tested).

- **`mod_index.rs`** — SHA256-based mod identification against per-game SQLite snapshots published to R2. `ensure_index` (fire-and-forget from the `lib.rs` setup hook) reads the catalog manifest at `https://index.modrex.net/catalog/latest.json` and refreshes each game with a valid saved path: the snapshot downloads to `app_data_dir()/indexes/<game_id>.db`, skipped when the sha256 recorded beside it in `indexes/<game_id>.json` already matches the manifest, and every download is verified against the manifest size and sha256 before an atomic `.tmp`-then-rename write. Snapshots keep the schema `games`, `sources`, `mods`, `files`, so the query layer is unchanged from the monolithic era. The frozen `modrexio/modrex-index` release serves only desktop versions through 0.12.2 and is never written from this repo. `query_sha256(conn, sha256, game_name)`, `query_by_name(conn, name, game_name)`, and `query_mod_by_id(conn, mod_remote_id, game_name)` (newest indexed file for a known modworkshop id, used to enrich embedded-id matches) are private helpers that take a `&rusqlite::Connection`, testable with in-memory SQLite. All three join `files` to `mods` to `sources` to `games` and filter by `games.name = game_name` so a PD2 hash never matches a PD3 mod. `lookup_sha256(app, sha256, game_id, game_name)` is the public wrapper; callers pass `cfg.game_id` and `cfg.index_game_name`. `open_index(app, game_id)` opens the per-game db once, falling back to the legacy monolithic `mod-index.db` when absent, so a caller can run several queries against one connection: `upgrade_negative_ids` and `identify_untracked` both use it instead of reopening per lookup (`get_installed` is a hot path: startup, window focus, path changes). Both name-matching callers try the folder-derived name first and then the name the mod declares in its own `mod.txt` (`identify.rs::declared_mod_name`, Directory-unit targets only). The folder is whatever the archive unwrapped to, which for a GitHub source zip is the repository plus branch (`PD2-DiscordRichPresence-main`) and matches no mod page, while the declaration is the title the author publishes under. Measured against the reporter's real 31-mod install: 3 more mods identified, 0 wrong, and the one genuinely ambiguous declaration (`Silent Assassin`) still refused. It is strictly additive — a folder-name hit is never overridden, since a declaration can also be _worse_ (`VanillaHUDPlus`, no spaces, matches nothing). `query_by_name` returns `Some` only when exactly one mod matches (ambiguous = `None`) **and** that one match falls on a word boundary. LIKE has no notion of a word, so a folder named `Bag Contour` matched the unrelated mod `Blue Bodybag Contour` and took its identity — measured against two real installs, the boundary rule removes exactly that case and keeps every legitimate partial match (`Useful Bots` → `Useful Bots: Future Edition`, `Ammo Pickup Amount in HUD` → `Show Ammo Pickup Amount in HUD`). It is deliberately subtractive: it is applied to the single surviving candidate, never used to pick between several, so an ambiguous set stays refused rather than being resolved onto a mod the guard was already rejecting. **`files.remote_id` (and therefore `InstalledMod.file_id`) is positive for a ModWorkshop file and negative for a ModWorkshop link** — see `apps/index/AGENTS.md`; a mod whose page only links off-site has no file id to carry, and the two id spaces overlap, so the sign is what keeps `findSuspectDuplicateGroups`' game-wide grouping by file id sound. Uses `rusqlite` with `features = ["bundled"]`.

- **`news.rs`** — scrapes `paydaythegame.com`'s per-game news category page (`category_slug`: `"pd2"` → `payday2`, `"pdth"` → `theheist`, else `payday3`) for the News tab. **Fetches via a `curl` subprocess, not `reqwest`**: the site's Cloudflare bot management 403s every library HTTP client tried (`reqwest`, .NET `HttpClient`) regardless of headers — a TLS/HTTP2 fingerprint check — and a renderer-side `fetch()` is blocked too since the site sends no `Access-Control-Allow-Origin` header; `curl.exe` is the one client that passes (verified live), so `curl_fetch` shells out to it with `creation_flags(0x08000000)` on Windows, matching the `reg query`/`powershell` subprocess pattern in `launchers/`. `parse_news_html` (pure, HTML-in/`Vec<NewsItem>`-out) and `extract_total_pages` (parses the WP-PageNavi block — the total is the max page number across every `.wp-pagenavi a` link plus the `.current` span, since WP-PageNavi omits the link to whichever page you're already on) are both unit-tested against saved fixtures. `fetch_news`/`refresh_news` (page 1 only) are TTL-cached to `app_data_dir()/news-{slug}.json` (1 hour, same atomic `.tmp`-then-rename write as `mod_index.rs`); `fetch_news_page(game_id, page)` fetches any other page uncached. All three return `NewsResult { items, total_pages }`.

- **`storage.rs`** — backs the Settings > Storage section. `get_storage_usage` reports on-disk sizes of the thumbnails cache (`app_cache_dir()/thumbnails`), `mod-index.db`, and the `news-*.json` caches — the renderer's localStorage mod-metadata cache is sized/cleared on its own side (`modCache.ts`), since Rust can't see localStorage. `clear_thumbnail_cache` / `clear_index_cache` / `clear_news_cache` delete each and return the bytes freed, leaving the containing directory in place so the cache refills; `remove_file_freed` tolerates a live handle (returns 0 rather than erroring, e.g. mod-index.db mid-query on Windows). `dir_size`/`remove_files_in` are flat, files-only helpers matching `thumbnails::cleanup_dir`'s flat-cache assumption. The destructive counterpart is `settings.rs`'s `reset_app_settings`.

- **`analytics.rs`** — anonymous, opt-in GA4 usage telemetry via the Measurement Protocol, sent from Rust. Read `.agents/rules/analytics.md` before changing it.

- The modworkshop API at `api.modworkshop.net` requires a `User-Agent` header or returns 403.

- **Discord Rich Presence** (`commands/discord.rs`): a dedicated worker thread owns the Discord IPC client (connect retry 15 s, keepalive 30 s); `lib.rs` starts it with the persisted `discord_rich_presence_enabled` setting (default on). The renderer sets the displayed game via `update_discord_presence` (an mpsc send to the worker); the Settings toggle calls `set_discord_presence_enabled`, which flips the worker's shared `AtomicBool` and persists the setting — disabling clears the presence on the next worker wake, no restart needed.
