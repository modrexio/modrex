# Launchers (`src-tauri/src/commands/launchers/`)

Paths are relative to `apps/desktop`.

- **`launchers/`** — split into focused files so touching one launcher never requires touching another:
    - `types.rs` — `GameDef` struct (`name`, `executables`, `process_names`, `steam?`, `epic?`, `xbox?`), its `resolve_executable`/`is_installation` pair (see the split described under `mod.rs`), and the `Launcher` trait (`id`, `is_installed`, `find_game`, `identify_path`, `launch`)
    - `games/pd3.rs`, `games/pd2.rs` — one file per game; add new games as `games/<name>.rs`
    - `steam.rs` — Windows: `reg query` for install path, then walks `libraryfolders.vdf`; Linux: checks `STEAM_DIR`, `XDG_DATA_HOME`, snap, flatpak paths. `find_game` requires `is_installation` to hold for the candidate folder — a leftover folder without the game is not counted as installed. The Windows `reg query` result is cached in a `OnceLock<Option<String>>` for the process lifetime — never call `reg query` for Steam's install path outside this helper. The query runs through `run_bounded` (5 s).
    - `epic.rs` — reads `%PROGRAMDATA%\Epic\...\Manifests\*.item` JSON, then checks the manifest's `InstallLocation` with `is_installation`: a manifest outlives the install it describes, and an unchecked stale one used to win the probe order over a store that really had the game
    - `xbox.rs` — `find_in_drives` scans every subdirectory of each mounted drive root for `{dir}/{game.name}/Content/` containing the xbox executable; falls back to `find_via_package_manager` (PowerShell `Get-AppxPackage`, via `run_bounded` with a 15 s cap) for deeply nested installs; launches via `gamelaunchhelper.exe`. Xbox game path always ends in `/Content`. **`fixed_drive_roots` gate** (raw `GetLogicalDrives` + `GetDriveTypeW` externs — no windows crate dep; neither call does volume or network I/O): drives come from the live mount bitmask (A–Z, never a hardcoded letter list — a game drive on `H:` is a real setup) and only `DRIVE_FIXED` volumes are scanned, because the per-subdirectory stats block for the SMB redirector timeout on disconnected network/VPN drives and can stall on empty card readers — the cause of a real "Modrex is not responding" startup freeze — and Xbox installs only ever live on fixed NTFS volumes.
    - `mod.rs` — orchestration (`identify_launcher_for_path`, `launch_with`, `all_launchers`) + all Tauri commands. `game_def_for_id(game_id: &str) -> &'static GameDef` maps `"pd2"` to `&PD2`, `"pdth"` to `&PDTH`, `"cb"` to `&CRIMEBOSS`, `"raid"` to `&RAID`, anything else to `&PD3`. Marker files for `identify_launcher_for_path`: `steam_appid.txt`, `.egstore/`, `MicrosoftGame.config`. **Marker files are not universal** — a Steam PAYDAY 3 folder ships no `steam_appid.txt`, so this returns `manual` for it; never re-derive a launcher the user chose explicitly. `configure_game_path(None)` validates the existing saved path first (via `GameDef::is_installation`) and preserves the saved launcher as-is — it does not re-run `identify_launcher_for_path` on valid paths, because doing so clobbers games without marker files. **Which copy of the game to use is decided by `plan_resolution`, and it is the load-bearing part of this module.** Two stores' copies of one game are separate installs that share no files — each has its own mods folder and its own `.modrex.json` — so pointing at the wrong one makes an installed mod list read as empty. `Resolution` has four cases: `Keep` (settled copy still present — probes nothing, the steady state), `Refind(launcher)` (settled copy gone — probed under **that launcher only**, so a moved Steam library resolves while a copy that is merely mid-update reports missing instead of the game being handed to another store), `Missing` (settled on a hand-picked folder that is gone — nothing to probe), and `Settle` (not yet pinned — probe every store and choose via `pick_install`, which prefers the copy that already holds a `get_state_path` file). `install_pinned` is set by every write that resolves a copy, so `Settle` runs at most once per game; it is absent from settings files written before this existed, which is what makes an existing install re-choose once against the mod list on disk instead of staying on whichever store came first in the probe order. Never reintroduce a first-hit-wins detection order: a Steam copy installed after the fact used to take the game away from the Microsoft Store copy holding the mods, silently and permanently. **`GameDef::is_installation` vs `resolve_executable`**: the first answers "is the game here" and is what every recognition site must use (manual pick validation, saved-path revalidation, `Steam`/`Epic` `find_game`); the second answers "which executable do we spawn" and is launch-only. They differ because a Microsoft Store build has no Win64 bootstrapper at its root, only the nested WinGDK binary named by `XboxDef.executable` — validating a hand-picked Xbox folder against `executables` alone rejected a real installation. `select_game_install(game_id, launcher, game_path)` is how the Settings launcher picker switches between two stores' copies: it writes path and launcher together, taking the path from a `detected_installs` probe the renderer already ran so switching costs no new probing. `findGamePath()` in `api.ts` always calls `configure_game_path(null)` on every refresh — this is how stale paths (game uninstalled but folder left behind) get cleared. `is_game_running`, `launch_game`, `launch_without_mods`, `restore_mods`, `stop_game` all accept `game_id: Option<String>` and dispatch via `game_def_for_id` / `engine_for_game` — fully multi-game. The renderer passes `activeGame` to all five. The `-fileopenlog` warning in `TopBar` remains PD3-only (guarded by `activeGame === 'pd3'`). Private `do_restore(game_path, cfg)` is the shared restore implementation called by both `launch_game` (best-effort, errors ignored) and `restore_mods` (errors returned). `launch_game` calls it first so mods left in backup from a prior "launch without mods" session are restored before the game starts. Both `do_restore` and `launch_without_mods` iterate `cfg.targets` — each target gets its own backup dir; `base/` exclusion applies only to the primary target (index 0).
