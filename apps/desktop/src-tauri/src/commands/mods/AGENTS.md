# Mods engine (`src-tauri/src/commands/mods/`)

Paths are relative to `apps/desktop`.

- **`mods/`** — the most complex module, split into focused subfiles. `mod.rs` holds all `#[tauri::command]` functions and re-exports; the logic lives in:
    - **`StateLocks` (in `mod.rs`)** — per-game async locks serializing every read-modify-write of a game's `.modrex.json`. `save_state` is atomic per _write_, but two interleaved commands (an `nxm://` install landing mid focus-refresh, say) can each read the same state and the second write silently drops the first's changes. Every mutating command takes the guard via `lock_game_state(&app, game_id).await` before its read-modify-write span. Keyed per game so different games stay parallel. **Never hold a guard across a network download** — acquire it around the disk-write + state span only, or a slow download blocks every other operation on that game.
    - `engine.rs` — `ModEngineConfig` parameterizes all engine behavior per game. Fields: `game_id`, `index_game_name` (matches `games.name` in `index.db` — "PAYDAY 3", "PAYDAY 2", "PAYDAY: The Heist", "Crime Boss: Rockay City", "RAID: World War II"), `state_filename`, `targets: &'static [ScanTarget]`. `ScanTarget` holds `tag: &'static str`, `unit: ModUnit`, `mods_subpath`, `disabled_subpath`, `backup_subpath`. `ModUnit` enum: `File { extension, disabled_suffix, priority_prefix }` for UE pak games (PD3 and Crime Boss, both UE 4.27 — same `.pak`/`~mods` convention); `Directory { entry_markers, scan_markers, index_gated_markers, excluded_names, priority_prefix }` for Diesel/BLT games (PD2, PDTH) and the `ue4ss_mods` target on PD3/Crime Boss. **`entry_markers` vs `scan_markers`**: `entry_markers` drives archive classification during install (`classify_archive_dirs`, `is_unplaceable_pack`); `scan_markers` drives ambient disk scanning (`scan_active`, `scan_disabled` in `paths.rs`) — they are intentionally separate. PDTH mods has `entry_markers: &["mod.txt", "base.lua"]` (so DAHM sub-mod ZIPs install correctly) but `scan_markers: &["mod.txt"]` (so DAHM's ~40 bundled framework modules, which have `base.lua` but no `mod.txt`, are not auto-discovered as untracked mods) — `base.lua` instead sits in `index_gated_markers`, so those folders are _discovered_ but only tracked if their SHA256 matches the mod index. `excluded_names: &'static [&'static str]` is a third, name-based filter for when index-gating can't apply (a bundled folder's content is never hashed into the index at all — see the UE4SS block in `src-tauri/src/commands/AGENTS.md`); `scan_active`/`scan_disabled` skip any directory whose name appears there before even checking markers. `engine_for_game(game_id)` looks the id up in `GAME_REGISTRY` (`commands/games.rs`) and returns `Result<&ModEngineConfig, String>` — an unknown id is a hard error, never a silent PD3. `game_def_for_id` in `launchers/` does the same over the same registry. Helper fns: `mods_dir`, `disabled_dir`, `backup_dir`, `state_path`. Methods: `primary()` returns `&targets[0]`; `target_for(tag: Option<&str>)` routes by tag, falling back to primary for unknown tags; `disabled_suffix()`, `is_directory_unit()`, `priority_prefix_enabled()` (mirrors `disabled_suffix()`'s match-on-`ModUnit` shape — every site that calls `apply_priority_prefix` must gate on this first, since several targets, e.g. Crime Boss's `mods` and PD2/PDTH's `mods`/`mod_overrides`, manage order via something other than a filename prefix; `reorder.rs`, `folders.rs`, and `state.rs`'s `compact_folder_priorities` all gate on it). Every Tauri command in `mod.rs` takes a required `game_id: String` and starts with `let cfg = engine_for_game(&game_id)?` (the `?` surfaces an unknown-game error), passing `cfg` to all lower-level ops. `PD2_ENGINE` has two targets: `mods` (`entry_markers/scan_markers: &["mod.txt", "main.xml"]`) and `mod_overrides` (`entry_markers/scan_markers: &[]` — any directory). `PDTH_ENGINE` has two targets: `mods` (entry/scan markers as above) and `mod_overrides` (`entry_markers/scan_markers: &[]`). `RAID_ENGINE` has a **single blanket-accept `mods` target** (`entry_markers/scan_markers: &[]`, `excluded_names: RAID_INFRA_FOLDERS` = `base`/`downloads`/`logs`/`saves`) — **no `assets/mod_overrides` target**; the RAID domain fact in `apps/desktop/AGENTS.md` explains why one folder holds both script mods and asset packs. Markers can't be used because asset packs carry none; `excluded_names` mirrors BeardLib's own `_ignore_folders` (minus BeardLib itself, a normal installable mod), and the top-level `base` skip in `find_untracked_paks` additionally covers `mods/base/supermod.xml`. `PD3_ENGINE` has two targets: `paks` (primary, `File` unit, `.pak`/`~mods`) and `ue4ss_mods` (secondary, see the UE4SS block in `src-tauri/src/commands/AGENTS.md`). `CRIMEBOSS_ENGINE` has three targets, and unlike every other multi-target game its **primary** is the `Directory` one: `mods` (no markers — blanket-accept, same shape as PD2's `mod_overrides`) rooted at `CrimeBoss/Mods`, then `paks` (legacy `File` unit, `.pak`/`~mods`, same convention as PD3) rooted at `CrimeBoss/Content/Paks/~mods`, then `ue4ss_mods` (see the UE4SS block in `src-tauri/src/commands/AGENTS.md`). New installs always land in `mods` because `resolve_archive_download` dispatches on `cfg.primary().unit`; `paks` is reachable only via `target_for(Some("paks"))` (ambient scan/enable/disable/uninstall of pre-existing loose-triplet installs, never new installs). See the Crime Boss key domain fact in `apps/desktop/AGENTS.md` for why.
    - `types.rs` — `InstalledMod`, `ModFolder`, `ModsState`, `InstalledResponse`, `TopLevelItem`, `UpdateStatus`. **`UpdateStatus` (`Known`/`Unknown`/`Outdated`) replaced the old habit of encoding this in the version STRING** as `"unknown"`/`"outdated"`, which worked only because neither is a plausible ModWorkshop version and forced every reader to know both sentinels. Per-source version semantics do not fit one overloaded string either: Nexus search returns no version at all, and Steam Workshop has update timestamps rather than versions. `Outdated` specifically means a name match succeeded AFTER a SHA256 check against the index's current file already failed, so the installed bytes are known stale; `Unknown` never surfaces an update, because a mod with nothing comparable would nag forever. State files predating the field are migrated in `read_state` (NOT `reconcile_state`, which has two early returns that would bypass it) and the version is cleared, so a sentinel can never be compared as a real version. `InstalledMod.location: Option<String>` — scan target tag; `None` = primary target (backward-compatible), `Some(tag)` routes all ops to the named `ScanTarget`. Carries `#[serde(default, skip_serializing_if = "Option::is_none")]` so state files without it still deserialize.
    - `naming.rs` — `strip_priority_prefix` / `apply_priority_prefix` (filenames on disk are always `NNN_name.pak`), `pak_filename`, `hash_filename`, `make_uid`
    - `paths.rs` — `mods_base` / `disabled_base` / `get_state_path` / `active_mod_path` / `disabled_mod_path` / `find_untracked_paks`. `find_untracked_paks` iterates all `cfg.targets`; skips any target whose backup dir exists; builds a per-target known set by stripping the `"<tag>:"` prefix from keys in the caller's `known: HashSet<String>`; returns `Vec<(String, bool, Option<String>)>` — (rel*path, is_enabled, location_tag). Callers must build known keys as `format!("{}:{}", m.location.as_deref().unwrap_or(""), rel_path)`. **Host-pack paths**: `resolve_host_mod_dir` finds an installed host mod's on-disk folder by modworkshop id (from state; active → disabled → conventional name); `host_pack_dir` returns where an installed host pack lives (`<host>/<subpath>/<filename>`); `host_pack_disabled_dir` is the Modrex-managed disabled location \_outside* the host (`mods/disabled/host-<id>/<filename>`).
    - `state.rs` — `read_state`, `save_state` (atomic: writes to `{name}.tmp` then `fs::rename` over the real file — never revert to a direct `fs::write`), `get_folder_path` (recursive, builds slash-separated path from `parentId` chain), `reconcile_state` (marks missing files `missing: true`; migrates legacy `.disabled` paths; migrates `.pd3mm.json` → `.modrex.json` on first run; when backup dir exists: File-unit games read state from inside the backup because the whole folder was renamed; Directory-unit games read from the normal `state_path` because the state file stays in `mods/` and only user mod dirs were moved). `reconcile_state` also: **purges framework-only entries** — on every load, drops entries with no `file_id` and no `remote_id` (i.e. Modrex-installed or identified-by-any-source entries are always kept) that are _either_ missing all of the target's `scan_markers` files on disk (catches DAHM framework modules that were auto-discovered while the `scan_markers`/`entry_markers` split didn't exist yet) _or_ whose filename is on the target's `excluded_names` list (catches UE4SS bundled framework sub-mods collected before `excluded_names` existed — their marker file is still genuinely present, so the first check alone never catches them; Modrex-installed entries with a `file_id` are never touched); removes phantom folders (folders with no mods, no child folders, and no active directory — disabled dir is ignored so a leftover `disabled/` subdir doesn't block cleanup); calls `compact_folder_priorities` to renumber folder disk names to sequential `(1, 2, 3, ...)` within each parent scope (repairs gaps from prior bugs). **Two identity migration/repair passes**, both one-time self-healing that runs on every load until there's nothing left to fix: (1) backfills `remote_id` for a ModWorkshop entry identified before `remote_id` existed for that source — its `id` already IS the real ModWorkshop id (the only meaning `id` ever had before it became opaque for every source, see `sources.rs`'s `source_native_local_id`), so this is a plain fill-in, never a re-derivation, and it must run before `identify.rs`'s `upgrade_negative_ids` — which otherwise can't tell "genuinely never identified" apart from "identified long ago, just missing this new field," and its fuzzy SHA256/name fallback wipes the stored version and marks the mod Outdated on a name match, which must not fire as a side effect of a data migration; (2) recomputes `expected = source_native_local_id(&m.source, remote_id)` for any entry with `remote_id.is_some()` and overwrites `m.id` if it disagrees, repairing a source-native id that was ever wrongly promoted to another source's id (the root cause of a real observed bug: an exact SHA256 hit across a cross-posted file let a Nexus-tracked entry's `id` get silently reassigned to an unrelated ModWorkshop id before `upgrade_negative_ids`'s `remote_id.is_some()` guard was fixed). It also drops records that `superseded_records` finds: an older file's record at a path a newer file of the same mod also claims, which replacing installs used to leave behind. Both passes fold into the same single `save_state` call as everything else above.
    - `zip.rs` — multi-format archive support. `ArchiveFormat` enum (`Zip`, `SevenZip`, `TarGz`, `TarXz`, `Rar`) + `detect_archive` (magic-byte dispatch). Public API: `list_pak_entries`, `extract_entry`, `extract_dir_entry`, `extract_archive_flat`, `classify_archive_dirs`, `is_unplaceable_pack`, `resolve_archive_download`, `mark_archive_files`, `compute_sha256`. **Format dispatch**: all five formats share one enumerator — `list_entries` returns `Vec<ArchiveEntry { name, is_dir }>`, and the listing/classification operations (`list_pak_entries`, `classify_archive_dirs`) are pure functions over it; only extraction stays per-format because unrar can only extract to a directory (it can't expose a per-entry reader). `compute_sha256` streams the file in 64 KB chunks via `spawn_blocking` rather than buffering it whole. **Zip-Slip invariant**: every directory extractor (`extract_dir_*`, `extract_flat_*`) must route its destination through `safe_dest`, which rejects entries with `..`, absolute, or drive/UNC-prefix components; RAR extraction additionally validates entry names before `extract_with_base` (which writes by internal name). `resolve_archive_download` returns `ResolvedArchive` (a type alias for `Result<(PathBuf, Option<PathBuf>, Option<String>), String>`) — the third element is `location_tag` (`None` for primary, `Some(tag)` for secondary). For Directory targets it runs `classify_archive_dirs(names, cfg)`, which tags every mod dir with its destination: marker dirs (`mod.txt`/`main.xml`, at any depth via `rfind`) → their target; marker-less dirs at the **same depth** as marker dirs (or every top-level dir when the archive has no markers) → the override target; an explicit `assets/mod_overrides/<name>/` segment unwraps to the dir _inside_ it (handles packs double-wrapped in the game path). A single dir resolves directly; multiple dirs emit `ZIP_MULTI_PAK` with a single top-level `targetTag` when all entries share one target, or a parallel `entryTags` array when the archive spans targets (a mixed modpack) so the picker routes each entry independently. Two guards run before classification (PD2 only): `detect_host_pack` (see `host_mods.rs`) returns a `HOST_MOD_PACK` sentinel for content packs that install _inside another mod_, and `is_unplaceable_pack` returns `UNRECOGNIZED_ARCHIVE` for a flat folder of loose files (no marker, no nested asset structure) that can't be placed in any scan target. **UE4SS routing** (both `resolve_archive_download`'s File-unit branch and `resolve_crimeboss_archive`): when an archive has zero `.pak` entries, before erroring it first checks `has_ue4ss_loader_signature` (a top-level `UE4SS-settings.ini` — the one marker that's only ever present in the _full_ loader package, never a standalone sub-mod, since the bundled framework sub-mods ship alongside it with the exact same `Scripts/main.lua` shape a real sub-mod has) and emits an internal `UE4SS_LOADER:<zipPath>` sentinel (handled entirely in `mod.rs`, never reaches the renderer); if that's absent, `try_classify_as_directory_target` falls back to `classify_archive_dirs` against `cfg.targets` (which already includes `ue4ss_mods` for PD3/Crime Boss even though it's never primary) to catch a standalone Lua sub-mod archive. Each format has private helpers (`_zip`, `_7z`, `_tar<R>`, `_rar`). **sevenz-rust callback invariant**: the `bool` returned by the `decompress_with_extract_fn` closure controls iteration — `Ok(false)` stops, `Ok(true)` continues. Non-matching entries must drain their bytes via `std::io::sink()` before returning `Ok(true)` to stay stream-aligned in solid 7z archives. **unrar extraction pattern**: `open_for_processing()` uses a typestate loop — `archive.read_header()` moves `archive` into the returned `Header`; `header.skip()` and `header.extract_with_base(dir)` move it back. RAR extraction writes to a temp dir (the unrar API can only extract to a directory, not a single file path) then copies to `dest`; cleanup is guaranteed via an IIFE closure. `mark_archive_files` returns `(Vec<InstalledMod>, bool)` — the bool is `true` when at least one mod was newly checked (dirty flag for the caller to persist state). Skips mods where `archive_broken.is_some()` so repeated calls are O(1). `InstalledMod.archive_broken: Option<bool>`: `None` = unchecked, `Some(false)` = clean, `Some(true)` = broken; persisted in the state file so magic-byte scanning is amortized across launches.
    - `install.rs` — `install_mod_from_path`, `uninstall_mod_op`, `enable_mod_op`, `disable_mod_op`. All accept `cfg: &ModEngineConfig` and a `target: &ScanTarget` (derived via `cfg.target_for(m.location.as_deref())`). `install_mod_from_path` sets `location: None` for the primary target, `Some(target.tag)` for secondary (uses `std::ptr::eq(target, cfg.primary())`). File ops use extension rename / file copy / remove*file; Directory ops use dir move / recursive copy / remove_dir_all. Priority prefix applied only when `target.unit.priority_prefix` is true. `enable_mod_op`/`disable_mod_op` special-case `target.tag == "ue4ss_mods"`: call `ue4ss_modstxt::sync_enabled` and flip the tracked flag, then `return` *before* the file-move block runs — see the UE4SS block in `src-tauri/src/commands/AGENTS.md` for why moving the folder would do nothing. `launch_game` and `launch_without_mods` both call `maybe_suppress_crash_reporter` before spawning, so any future cleanup-only setting should stay launcher-gated and best-effort. `uninstall_mod_op` removes only the selected mod files and leaves now-empty app folders in state/on disk; folder removal is explicit via `delete_folder_op` or reconciliation of phantom folders whose active directory is gone. **Host packs** (`location` starting `host:` — see `host_mods.rs`) take dedicated branches in every op: `install_host_pack_op` extracts a set into the host mod's folder and records it; `uninstall_mod_op` removes from the active \_or* disabled location; `enable_mod_op`/`disable_mod_op` call `move_host_pack`, which moves the set between the host's subfolder and `mods/disabled/host-<id>/` (flipping only the `enabled` flag would leave the set loading in-game).
    - `host_mods.rs` — declarative registry of **host mods**: mods whose add-on content packs install _inside another mod's folder_ rather than at a scan-target root (the canonical case is Menu Backgrounds, modworkshop `17160` → `Assets/`). `HOST_TARGETS` carries `host_mod_id`, `host_name`, `subpath`, a filename `signature` + `min_matches`, and `bundled` (set names the host ships itself, e.g. Menu Backgrounds' `"The Diamond"`). `detect_host_pack(names)` recognizes a pack by content signature (rejecting anything with a `mod.txt`/`main.xml` marker). A recorded pack's `InstalledMod.location` is `host:<id>:<subpath>`; `parse_host_location` / `host_target_by_id` read it back. The host's on-disk folder is always resolved from installed state by id, never assumed from its name. **Recovery after a state rebuild**: host packs live inside another mod, so the scan-target walk can't find them — `find_untracked_host_packs` (in `paths.rs`) scans the host's `subpath` (and the disabled area) for untracked set folders, excluding `bundled` defaults. `get_installed` then identifies each by its representative file's SHA256 against the index (`hashable_file_for_mod_dir` + `lookup_sha256`): a hit restores the real identity (`id` via `sources::source_native_local_id`, `remote_id`, name/version), a miss leaves an unidentified, folder-named entry whose stored sha256 lets a later index update upgrade it. **Modrex installs and tracks the files only — it never writes a host mod's own runtime/in-game settings to "activate" a pack** (e.g. Menu Backgrounds' `BGsSet` option is the user's to set in-game). Note: a host pack is only index-identifiable if its source mod is in `index.db` — e.g. a large RAR was unindexed until the `modrex-index` RAR/7z size cap was raised (a backfill run picks up the backlog).
    - `reorder.rs` — `reorder_mods_in_folder_op`, `move_mod_to_folder_op`, `reorder_children_op`
    - `folders.rs` — `create_folder_op` (idempotent: reuses an existing folder with the same `display_name` under the same `parent_id` instead of creating a duplicate record — callers that create folders in a loop, e.g. `ZipPickerModal`'s auto-folder-creation, can safely call it repeatedly for the same path without producing two state records that collide on one on-disk directory), `move_folder_op`, `rename_folder_op`, `delete_folder_op`
    - Key invariants:
        - `disabled_mod_path` appends `.disabled` to the `.pak` filename for File mods — the extension change is what disables mods (Unreal scans all subdirectories of `Paks/`, so subdirectory alone is insufficient). For Directory mods, disabling moves the folder into `disabled/`.
        - `get_installed` accepts `game_id: Option<String>` and uses `engine_for_game` to select the correct engine. All games are handled; there is no pd3-only guard.
        - `get_installed` identification pipeline: (1) SHA256-then-name index lookup upgrades entries with no `remote_id` yet; (2) name-suffix pass re-assigns identity to entries that still lack one; (3) untracked mods are auto-folder-created, reconciled by SHA256, then identified by hash → embedded modworkshop id → name (precedence detailed below). New untracked entries use `by_uid.entry().or_insert(...)` — existing entries are never overwritten. The command body is a thin orchestrator; each stage lives in a named helper: `upgrade_negative_ids`, `regroup_negative_ids_by_name_suffix`, `ensure_untracked_folders`, `hash_untracked`, and `identify_untracked` (Phase 1 relocation + Phase 2 identify). **Phase 1 answers a different question from Phase 2** — "are these the files this record already owns, moved" rather than "which catalogue mod is this" — and a shared hash does not answer it: an Unreal pak can be a container stub that unrelated mods ship byte-identical copies of, and the filename Phase 1 writes is what uninstall later deletes. `relocate_moved_mods` therefore groups the whole scan by target and hash before deciding anything, and adopts a candidate only when the record has no files of its own left (`installation_present`, which refuses on a filesystem error rather than reading it as absence), both sides sit in the same target, that target declares no companions, and the group holds exactly one record and one candidate. It returns the untracked _indices_ it adopted, not hashes: Phase 2 skips those, so every refused candidate is still identified on its own instead of vanishing. **Phase 2 precedence per mod**: exact SHA256 hit → **embedded modworkshop id** (Directory-unit mods only — `embedded_modworkshop_id` parses one format per BLT family, all verified against real downloads: BeardLib's `main.xml` `<AssetUpdates provider="modworkshop" id="N" version="V">`, RAID-SuperBLT's `supermod.xml` `<update provider="modworkshop" identifier="N">` with the version on the root `<mod>` element, and legacy RaidBLT's `mod.xml` `<auto_updates provider="modworkshop" id="N" version="V">`; enriched via `mod_index::query_mod_by_id`; preferred over the fuzzy name match because the embedded id survives version drift) → **name fallback** (`query_by_name` → numeric-stripped filename → `hash_filename`). `hashable_file_for_mod_dir` prefers `main.xml` → `supermod.xml` → `mod.xml` before the pak/first-file fallbacks, mirroring the indexer's `chooseMarker` so both sides hash the same representative file. **The marker-less fallback is a cross-language contract, not a coincidence**: both sides take the path whose UTF-8 bytes sort first, relative to the mod's own root, and the vectors live once in `apps/index/marker-contract.json` with a test on each side (`marker_contract_tests.rs` here, `pnpm test:marker-contract` there). A directory-by-directory walk is not the same ordering — it disagrees where a file and a folder share a stem — and neither is a locale-aware comparison, which is what made ModWorkshop 31190 (`vityaz_reload.animation` next to `vityaz_reload_not_empty.animation`) unidentifiable. Changing the ordering on one side alone strands every marker-less mod whose pick moves. An embedded-id mod's installed version is its own `main.xml` declaration, falling back to the index's current version so a drifted-old install reads as outdated rather than nagging a false "unknown" update. `upgrade_negative_ids` (renamed from `upgrade_negative_ids_by_sha`; the name predates `InstalledMod.id` becoming opaque for every source — it now gates on `m.remote_id.is_some()`, never `id`'s sign, and skips an already source-tracked entry, e.g. Nexus, outright rather than only checking `id >= 0`) tries SHA256 first, then falls back to `lookup_by_name(m.name)` on every miss — not just at first discovery. This matters because SHA256 misses permanently once a mod's modworkshop file is updated after install (the old installed bytes can never match a newer hash again); without the name retry, a mod that missed both checks once (e.g. because the local index happened to be stale at that exact moment) would stay "Unknown" forever, since this was previously the _only_ re-identification pass that runs on every refresh — the user would have had to wipe `.modrex.json` to force a fresh `identify_untracked` pass. On a hit it sets both `id` (via `sources::source_native_local_id("modworkshop", &remote_id)`) and `remote_id`, never just `id` alone, and the SHA256 branch must also move `update_status` to `Known`: the entry it is repairing was left `Unknown` by the pass that failed to identify it, and `useModData` skips an `Unknown` mod for updates forever, so a self-healed mod would silently never see an update again. Returns `bool` — both early-return paths (`mods_hidden` and `untracked.is_empty()`) check it and call `save_state` when true, so a recovered identity is never lost on the next write.
        - `install_mod` stores the **mod-level** version from `/mods/{id}` (not the file-level version from `/files/latest`). It inherits `folder_id` from existing state when the caller omits it.
        - **Multi-file installs**: `install_mod_from_path` finds `existing` by `uid` only (not `id`). `install_mod` pre-removes the old pak when exactly one same-id entry exists — never do this inside `install_mod_from_path`.
        - **ZIP installs**: `install_from_zip_entry` uid is `{file_id}_{entry_stem}`; SHA256 match reuses existing uid so reinstall moves in-place. `folder_id` is always caller-provided (never inherited from existing entries). `location_tag: Option<String>` param routes the install to the correct `ScanTarget`. Mirrors `install_mod`'s pre-removal via `stale_entry_for_zip_install`: every record of this mod from an older file that is the same entry (`{old_file_id}_{entry_stem}`) or sits at the path this install writes to is removed first. When there is none and the resolved uid doesn't match any existing entry, the mod's only other entry is removed instead. A stale entry whose path another record shares (Crime Boss puts all of a mod's entries in one folder) only loses its record — unless its uid starts with `{file_id}_`, i.e. it is an archive-scheme sibling of the file being installed right now: a multi-entry batch install (ZipPickerModal select-all) installs sequentially, so without that exclusion each entry saw exactly one same-id entry (the sibling installed a moment earlier) and deleted it, leaving only the last selected entry. The pre-removal exists because without it, a mod whose file packaging changes between a bare `.pak` (uid = `file_id`) and an archive (uid = `{file_id}_{entry_stem}`) leaves the old uid orphaned as a second tracked entry for the same mod, which also suppresses the update prompt (the dedup-by-id check in `useModData`'s `updatable` sees the new version already installed under the other uid).
        - `InstalledMod.uid` has `#[serde(default)]` so state files predating the uid field still deserialize
        - **Multi-target routing**: `cfg.target_for(m.location.as_deref())` is the canonical way to get a mod's `ScanTarget` in any op. Folder ops (`create_folder_op`, `move_folder_op`, etc.) always use `cfg.primary()` — app folders live only in the primary target's directory tree.

**Crime Boss enable/disable does not work by moving files** — `commands/mods/crimeboss_settings.rs`. Reverse-engineered against real installs: the game's UGC mod-loader tracks each mod's active state in its own JSON file at `%USERPROFILE%\Saved Games\CrimeBoss\<platform>\Saved\ModSettings\<id>.json` (outside the game install dir entirely — the game redirects its UE `Saved/` folder there), read/written directly by the in-game Options > Mods screen. Moving a mod's files (to a `disabled` subfolder, or anywhere else) has zero effect on this — confirmed live: a mod Modrex moved to `Mods/disabled/<name>/` kept reading `"enabled": "true"` in its settings file indefinitely. The file's `<id>` is **not** derivable from the mod's display name — it's `lowercase(pak_filename without the "CrimeBoss-WindowsNoEditor" suffix)`, e.g. `DallasPDCrimeBoss-WindowsNoEditor.pak` maps to `dallaspd.json` (verified against 10+ real installed mods). Schema: a JSON array of `{"name": ..., "value": ...}` objects (values are strings, even for booleans — `"value": "true"`, not `true`); mods with author-defined custom settings have more entries in the same array that must survive untouched. `crimeboss_settings::sync_enabled` (called from `install.rs`'s `enable_mod_op`/`disable_mod_op`, gated by `cfg.game_id == "cb"`) finds the `enabled` entry and flips its value, leaving everything else alone. Two things this can't do anything about: (1) **the settings file doesn't exist until the game has launched with the mod present at least once** (created lazily, not at install time) — `sync_enabled` no-ops rather than synthesize a guessed schema for a fresh mod; (2) **the platform subfolder name is only verified for Steam** (`"steam"` maps to `"Steam"`) — anything else no-ops rather than guess at an unverified path. Mods built outside the ModKit's standard pipeline (pak doesn't end in `CrimeBoss-WindowsNoEditor`, e.g. older loose `~mods`-only mods like "Total Mission Value") have no UGC object and thus no settings file to sync at all — this is expected, not a bug. Resolved via the `USERPROFILE` env var, matching this codebase's existing pattern for OS-specific paths elsewhere (`epic.rs`'s `PROGRAMDATA` lookup) rather than the Windows known-folder API.

- **`mods/identity.rs` + `mods/diesel_signals.rs`** — **what an installed mod _is_, separately from where it can be downloaded.** `ModIdentity { namespace, key, evidence, confidence }` on `InstalledMod` answers "which project is this"; `source`/`remote_id` continue to answer "and which catalog entry does it correspond to". The two are independent: a mod distributed only from its author's own updater gets a real identity and no catalog link, and the renderer's `isIdentified`/`hasCatalogLink` split mirrors that. **`namespace` is a field, never a prefix parsed out of `key`** (`modworkshop`+`25629`, `pd2mods.z77.fr`+`Celer`, `github`+`owner/repo#Declared Name`, `paydaymods`+`silentassassin`), so two ecosystems cannot collide and no consumer has to know the key's shape; a namespace implies nothing about capability. `confidence` is derived from `evidence` by the single constructor and is never read back from disk, so the two cannot disagree.

    **The operation that establishes a catalog association records the evidence for it, in the same statement.** `InstalledMod::attach_catalog` / `from_catalog` (types.rs) write `source`, `remote_id`, the derived `id` and the identity together; nothing reconstructs provenance afterwards, and in particular `update_status` carries no identification history. What each path records: install → `InstallProvenance`; SHA256 index hit and Nexus MD5 archive match → `CatalogHash`; validated embedded BeardLib id → `EmbeddedCatalogId`; Nexus content lookup (published file name + size, or content folder segment) → `CatalogContentMatch`; index name match or a filename that is itself an id → `CatalogName`. `CatalogReference` means only "an older state file already carried this reference and how it was found was never recorded" — never claim an install that is not known to have happened.

    `resolve_identity` is pure, offline, and covers only mods with no catalog association: embedded catalog id → updater namespace → repository plus declared name → legacy namespace → name+author (`Candidate`, a guess that never counts as identified). `ensure_identities` fills the remainder from `get_installed` at all three exits and never recomputes an identity that is already recorded — a recorded identity describes the folder as of the scan that recorded it, exactly like `name`, `version` and `sha256` on the same record. Changing the extraction rules in a later release therefore needs a deliberate one-time clear of locally derived identities, not a rescan.

    The generic model knows nothing about mod files. `SignalSource` on `ModEngineConfig` says which vocabulary a game's mods speak (`Diesel` for PD2/PDTH/RAID, `None` for the pak games), and `diesel_signals.rs` owns every BLT and BeardLib rule, each of them forced by the ecosystem rather than chosen: `mod.txt` is scanned rather than parsed because 7.5% of shipped files are not valid JSON; a `simple_update_url` outranks the `updates` block because a whole family of mods declares the identifier of the _updater tool_ they share (twelve distinct mods collapse onto one key otherwise); a repository is never an identity on its own since surveyed repositories hold up to 130 mods; an `updates` entry with no host is a paydaymods.com record, dead since February 2020, kept namespaced for recognition with no update capability implied; and an `AssetUpdates` id is validated against the snapshot before it is trusted, because a third of them are template placeholders and at least one real mod ships another project's id.

`mods/` submodule uses `#[cfg(test)] pub(crate) use` to re-export private helpers so `tests.rs` can reach them via `use super::*`. The `::zip::` prefix is required in `tests.rs` to reference the external crate (not the local `mod zip` submodule).
