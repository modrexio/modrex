# Hooks (`src/renderer/src/hooks/`)

Paths are relative to `apps/desktop`. `useFolderActions` and `useModActions` are described with
the InstalledPage family in `src/renderer/src/components/AGENTS.md`.

**`hooks/useThumbnail.ts`** — Hook for thumbnail images. Initializes state synchronously from `getCachedThumbnailUrl` (local asset URL if already resolved this session); otherwise races `getLocalThumbnail` against a 50 ms timeout. A disk-cache hit wins the race, so the CDN is never touched; on timeout the CDN URL is shown **and kept for that mount** — never swap `src` after the CDN image may have painted, because the swap makes the webview re-load the image (visible flicker). The resolved local URL is still recorded so future mounts resolve synchronously. Consumers must render a placeholder for a `null` src (covers the sub-50 ms race window). The optional `full` param selects the original image instead of the 256 px small variant — see the variant policy in the `thumbnails.rs` section for which renders need which. Used in `ModCard` (full), `ModListRow` (small), and `ModDetailPage` (banner/`GalleryImage`/`LightboxImage` full, `DependencyRow` small) — never use a bare CDN URL for thumbnails. The one deliberate exception: user avatars in `ModDetailPage`'s members section load straight from `AVATAR_BASE_URL` (`users/images` on the storage CDN, `thumbnail_` prefix when `avatar_has_thumb`) — the disk cache and `thumb://` protocol only serve mod images (`mods/images`), and avatars are too small/rare to justify extending it.

**`hooks/useLoaderState.ts`** — the shared loader state behind `BrowsePage` and `ModDetailPage`, which previously kept near-identical copies (both of the bugs fixed in `fix(deps): surface install prompts on dependency rows` lived in that duplication). Returns `loaderState`, `setLoaderFlag`, `refreshLoader(id)`, `installLoader(loaderModId)`, and `loaderModIds`. `installLoader` is the single registry-driven dispatch — `viaModFlow` loaders (UE4SS) ride `api.installMod`, everything else calls `api.installLoader` — and **returns the post-install presence rather than assuming success**: a loader can be on disk and still unusable (SuperBLT on PD2's Diesel 3.0 branch), and an optimistic `true` made the UI claim Installed while the install flow reported it missing. The presence-check effects deliberately stay in the components: `BrowsePage` checks every loader with a mod page on activation, `ModDetailPage` only the loaders the open mod depends on. The deps-warning modal state stays per-component too (`BrowsePage` tracks which mod triggered it; `ModDetailPage` is inherently per-page). `NexusBrowsePage` has no deps-check logic at all — Nexus mods carry no modworkshop dependencies.

**`hooks/useModData.ts`** — coordinates display metadata and update observations without conflating them. ModWorkshop display summaries use `ids[]`; authoritative versions use `useModVersions`; Nexus keeps its separate detail-backed path and quota behavior. Cached display data renders immediately, thumbnails pre-warm, and a 30-second/focus loop rechecks TTLs even when installed IDs are unchanged. Update comparison groups all installed files for one mod: unknown/missing/failed/stale/unversioned remote state is never an update, comparable installed versions update only when every present entry differs, and the existing explicit `outdated` byte-identity signal remains eligible. The updates modal then fetches fresh detail and files, and `resolveUpdateTarget` (`updatePolicy.ts`) decides whether to install, ask which file to install, or report that Modrex cannot install it. It never navigates to the mod page or opens a browser. Mods whose summary says the download is a link, or that the author closed to mod managers, are never offered as updates.

**`hooks/installedUtils.ts`** — pure data helpers. **Three separate questions, three helpers, and mixing them up is the bug this split exists to prevent**: `isIdentified(m)` asks _what is this mod_ and reads `m.identity` at Exact or Strong confidence, so a mod published only on its author's own updater (`pd2mods.z77.fr:Celer`) is identified exactly as much as a ModWorkshop one, and a Candidate guess never counts; `hasCatalogLink(m)` (`!!m.remoteId`) asks _can we fetch it from a catalog_ and is what browsing, thumbnails, update checks, reinstall, the mod detail page and the Nexus-identify affordance all actually need; `identityKey(m)` is the grouping key, project identity first (namespace and key together, never the key alone) and the installed record only as a fallback; `withDeclaredMetadata(m)` swaps in the name, author and version a mod's own files declare when no catalog describes it, applied once at the top of `InstalledPage` so search, grouping and every row agree. When the split landed, every component call site turned out to want `hasCatalogLink` — only grouping and the Health Check's unidentified bucket wanted identity — so reach for `hasCatalogLink` unless you specifically mean "do we know what this is". `InstalledMod.id` remains the installed record's own key (React keys, DnD, command targets), never the project identity (see the `InstalledMod.id` domain fact in `apps/desktop/AGENTS.md`). `syntheticMod(ins)` constructs a fallback `Mod` object for unidentified and fetch-failed mods — the pattern is `apiMod ?? syntheticMod(ins)` after the skeleton guard, so unidentified mods render with their local name instead of a skeleton. `modworkshopRemoteIds(mods)` extracts real, deduplicated modworkshop ids for the handful of call sites that need to fetch fresh data by real id (e.g. dependency checks) — never pass a local `id` to a real API call. `getAllModsInFolder(mods, folders, folderId)` recursively collects all mods in a folder subtree (direct children plus nested folders); used for bulk enable/disable on folder toggle. `normalizeModScopes(mods)` — for rendering only, collapses multi-folder entries for the same identified mod only when some of those entries are at root (the split-install artifact where reinstalling puts some paks at root). Intentional multi-folder layouts (all entries in non-root folders) are left untouched. `foldersEmptiedByNormalize(raw, normalized, folders)` computes the folders whose entire subtree was pulled to root by that collapse — `computeChildren`'s optional `hiddenFolderIds` param (threaded from `InstalledPage` through `InstalledContext` to `FolderSection`) hides them, so a folder holding only a collapsed multi-pak mod (e.g. a skin archive in a folder plus its required bare pak at root) doesn't render as an empty duplicate next to the mod's root card; folders that were already empty before normalization (fresh drop targets) stay visible. Called in `InstalledPage` as `renderMods = normalizeModScopes(displayMods)` before passing to `computeChildren`. `computeChildren(mods, folders, parentId, visibleFolderIds?)` builds and sorts children (mods before folders, both descending by priority) — filters out folders that have no mods in the normalized array (prevents empty auto-created folders from appearing); the optional `visibleFolderIds` set filters folders not matched by search. `groupChildren` collapses consecutive mod runs into `root-group` grid slots; `filterInstalled(mods, folders, query)` returns matching mods and the set of all ancestor folder IDs that must remain visible. `InstalledGroup = { key: string; id: number; mods: InstalledMod[] }` and `groupInstalledByIdentity(mods)` — groups by `identityKey` (`identity:<namespace>:<key>` when the project is known, else `id:N` for a catalog install, else `uid:X`); the canonical grouping used by the health check and the mod counter. `detailNavArgs(ins)` resolves the real remote id (+ `'nexus'` source flag when applicable) needed to navigate to `ModDetailPage`, uniformly for both sources via `remoteId`. `HealthSummary` and `computeHealthSummary(mods)` — purely local health categories (missing, archiveBroken, outdated, unidentified), no network. **`unidentified` means Modrex could not work out what the mod is at all**, not "not on ModWorkshop": a mod with a resolved local identity and no catalog entry is not a health problem and does not appear there. `outdated` needs `hasCatalogLink`, since "something newer exists" is unanswerable without a catalog. `outdated` catches two cases: `version === 'outdated'` (SHA256 mismatch, set by Rust) and stale duplicates from `findSuspectDuplicateGroups` (bare-uid + archive-scheme uid coexisting for the same `fileId`). `healthIssueCount` in `InstalledPage` sums missing + archiveBroken + outdated + unidentified to drive the badge on the health check button — dependencies and updates are intentionally excluded from the badge.

**`hooks/useDragDrop.ts`** — all reorder-DnD state and handlers. Reordering runs on **pointer events, not HTML5 drag**: `dragDropEnabled: true` in `tauri.conf.json` (required for the drop-a-file-to-install flow — Tauri's native `onDragDropEvent`, wrapped as `api.onFileDrop` and consumed by `useFileDropInstall`/`FileDropOverlay`, is the only way to receive dropped file _paths_) disables HTML5 drag events in the webview, so the hook implements dragging itself. `onModPointerDown`/`onFolderPointerDown` arm a pending drag that starts after a 5 px movement threshold (pointer-downs on `button, a, input, textarea, select, [data-no-drag]` never arm); `pointermove` hit-tests `document.elementFromPoint` against the `data-drop-mod`/`data-drop-folder-header`/`data-drop-empty-folder`/`data-drop-child` attributes via pure `compute*DragOver` functions returning a `DropTarget`, auto-scrolling near the edges of the container behind `scrollContainerRef`; `pointerup` applies the target (`applyModReorder`/`applyDropIntoFolder`/`applyChildDrop`/`applyNestFolder`). Escape cancels, and a capture-phase click listener (removed on the next tick) swallows the click the browser fires right after a drop so it can't open the mod detail page. Mods with `location` set (secondary-target, e.g. `mod_overrides`) are blocked from cross-folder drags and into-folder drops — `computeModDragOver`'s cross-folder path, `computeFolderHeaderDragOver`, `computeEmptyFolderDragOver`, and the apply-side guards in `applyModReorder`/`applyDropIntoFolder` all check `srcMod.location`. Same-scope reordering is still permitted.
